## 0. 总体节奏

```
M0 骨架就位 ──► M1 采集上报闭环 ──► M2 存储与查询 ──► M3 公开看板
                     │                                    │
                     └──► M4 计费/告警 ──► M5 一键安装 ──► M6 加固与上线
```

原则：**先打通端到端最小闭环，再逐层加厚**。任何阶段都不引入远程控制通道，
新增字段一律可选（保持 `/api/agent/v1` 向后兼容）。

本轮（第 128~131 项）是**上线前准备**：一份部署文档、Master 与 Agent 各一个一键脚本，
以及新增的 **Agent 自升级**能力。

自升级的取件**不复用公开的 `/dist/`**：`install.mode` 默认 `on_demand`，
只有存在未使用注册码时才开放，而节点装好之后注册码就被消费了——那条路随即关闭。
按它的语义这是对的（不该长期匿名分发二进制），但升级会被一起关死。
所以新增 agent 作用域的两个接口（节点令牌鉴权）：`releases/latest` 查版本、
`artifact` 流式下发构件并带 `X-Checksum-Sha256`。客户端侧三条硬规则：
**先校验后落地**（下载到 `.new`，哈希对上才改名，中途崩溃不留半成品）、
**绝不主动降级**（"比最新还新"也算无需动作，降级只能由运维显式指定）、
**替换失败必须还原**（不留"目标缺失 + 有 `.new`"的半套状态）。

写文档与脚本的过程又挖出 4 个真缺陷（`docs/01` 缺陷 44~47），都是"照着文档做就会踩"的那一类：

* **PowerShell 脚本在中文 Windows 上整份语法错误**：`.ps1` 有中文却**没有 UTF-8 BOM**，
  而 `powershell.exe` 5.1 只看 BOM 判断编码，回退到 GBK 后某个汉字的尾字节会吞掉紧跟的引号，
  整份脚本报十来处"意外的标记"、**完全跑不起来**，且与脚本逻辑毫无关系
  （英文 locale 不复现）。5 个 `.ps1` 全部加 BOM 后，用 PowerShell 自己的解析器数错误：全部 0 处。
* **BOM 又不能出现在分发的文本里**：一行安装命令是脚本块构造 API 喂 `irm` 的结果，
  开头的 `U+FEFF` 会被当成第一个标识符的一部分而直接失败。
  于是同一文件对两个消费者要求相反（**磁盘要 BOM、线上不要**），差异必须在一处抹平并两侧断言。
* **本机与 CI 的构建路径没注入发布标签**：Makefile 注了，`build.ps1 -Dist` 与 `ci-cross.sh` 没注，
  而后者才是这两条路径实际用的。后果是 32 位 ARM 节点自升级永远报"该平台未发布此版本"
  （`-X` 指向不存在的符号时 `go build` **不报错**，只是什么也不注入）。
* **`install.sh` 与发布布局对不上**：安装脚本取扁平路径（它不知道版本号），
  而 `dist pull`／后台发布页／README 用的是带版本的目录——按文档做完 `dist pull` 之后
  一键安装必然在"无法获取校验和"处中止。修复 = 把扁平路径作为**最新版本的别名**，
  与自升级共用同一套"什么是最新"的判定，因此两条链路不可能拿到不同版本。

冒烟新增第 8.6 节（24 项），刻意**真编两份不同版本号的 Agent**（1.0.0 与 9.9.9）跑完整链路：
版本发现 → 取件校验 → 实际替换 → 备份 → 再查（已是最新）→ 回滚；
另覆盖两个静默面：非点分目录（`nightly-*`）必须被忽略、未发布的平台要能报"该平台没发"
而不是"Master 没配好"。

### 第 139~143 项的验收标准（站点形态：公开看板与后台要不要分两个域名）

需求原文是"**这个公开看板和后台管理可设置是否分离成两个域名或者不分离只在一个站点下访问**"。
落到实现上是一簇**运行时设置项**（不是配置文件开关），验收标准如下：

- [x] 后台可切换，且**改完即时生效、不用重启**：设置项为 `site.layout`
      （`auto` 跟随配置文件 / `single` 同站 / `split` 分离）+ `site.public_hosts` /
      `site.admin_hosts` 两份域名清单，归在「系统设置 → 站点形态」分组
      （`internal/api/site_layout_test.go`：`TestSiteGateReadsSettingsPerRequest`——
      **门控只构造一次**，之后改设置，行为必须跟着变）。
- [x] 门控**按路径**判域名（`TestSiteGateSplitIsPathAware`）：同一个入口上 `/`、`/admin/`
      属于不同域名。这是"一个端口 + 两个域名 + 反代"的常态；只按入口判断等于没有分离。
- [x] `single` 是真的"同站"（`TestSiteGateSingleTreatsHostsAsOneSite`）：
      已配置的任一域名都能打开两边，不再保留"公开域名打不开 `/admin/`"这条规则。
- [x] **存量部署的行为一个字都不变**：默认 `auto`，且 `auto` + 未配管理域名时管理路径
      必须放行（`TestSiteGateAutoKeepsLegacyBehaviourWithoutAdminHosts`）——
      否则升级之后所有单域名实例的后台集体打不开。
- [x] **危险方向要挡住**：选 `split` 却缺任一域名清单时，保存返回 400 拒绝

本轮（第 119~123 项）做了两件互相印证的事：**接通「探测连续失败」告警**，以及
**把 Agent 侧 6 个零覆盖的包一次补齐**。

`alert.KindProbeFail` 此前是一条"只有壳没有芯"的规则——`CHECK` 白名单、`DefaultRules()`、
API、后台标签齐全，却没有代码发出这个事件。它要表达的那类故障（节点在正常上报、
资源也正常，只是探测目标不通）恰好是 `offline`（看 `LastSeen`）与
`cpu/mem/disk`（只看资源）都覆盖不到的。接通时定了四条口径：**权限/策略类错误不算失败**
（`icmp_not_permitted`/`blocked_target` 是"没测成"不是"测到了不通"，算进去会让所有
无特权节点永远在报警）、**粒度挂到目标**（`probe_fail:<target_id>`，否则两个目标各失败两次
就等于"连续 4 次"）、**"目标本轮没上报"不等于"恢复"**、以及**按轮去重**。
最后一条是真正的难点：Agent 每 30 秒探一轮而 `alertTick` 每 10 秒扫一次，
`LatestLatency` 又是持久的，不去重的话 `ConfirmN=3` 会在**一轮之内**被满足——
"连续 3 轮确认"静默退化成"失败一次即告警"。修法是新增单调递增的
`NodeRuntime.LatencyRound`（与样本替换在同一次 `Update` 里自增）+ 一张按 `(node, target)`
去重、按运行态裁剪的表；用轮次号而非时间戳，时钟跳变不会干扰判定。

Agent 侧补测试的过程**发现并修复了 8 个真实缺陷**（`docs/01` 缺陷 36~43），其中三个是
"线上一定在用、只是没人报"的量级：

* **ICMP 在回退路径上 100% 失败**：`udp4` 不可用时回退到原始套接字，但目标地址仍是
  按 `udp4` 造的 `*net.UDPAddr`，而 `ip4:icmp` 要 `*net.IPAddr`——`WriteTo` 每次返回
  `invalid argument`。Windows 与 FreeBSD 都走这条分支，等于这两个平台的 ICMP 探测
  **从未成功过一次**，而失败被归成 `timeout`/`other`，看板上表现为"这些节点的目标一直不通"。
* **EPERM 的文本是 `operation not permitted`**（含 `permitted` 不含 `permission`），
  旧分类只匹配后者，于是"没有 raw socket 权限"被归成笼统的 `other`。
* **`config.splitList("")` 返回空切片**，让 Master 下发 `"nic_exclude": []`，
  Agent 反序列化成非 nil 空切片、绕过 `!= nil` 守卫，把内置的 `lo/docker*/veth*`
  默认排除项整体抹掉——流量把容器网卡与回环一起算，数字凭空虚高。
  这是 `public.cards` 三态教训（不变量 6）在另一个字段上的重演，已补**生产端**护栏
  （直接断言报文里必须是 `null`）。

另外五个（SPKI 指纹不支持无填充 base64、`no route to host` 被报成「域名解析失败」、
`min == 0` 哨兵吃掉合法的 0 微秒样本导致 `min > avg`、`collector` 从不重建导致
网卡过滤项的改动永远不生效、`splitList` 不认制表符/回车生成幽灵条目）同属
"编译通过、单测全绿、日志正常"却行为错误的那一类，全部已修并各有护栏。

**M6 本轮实现备忘（6.2 / 6.6）**

*TOTP（6.2）*

- 动态码按 RFC 6238：SHA-1 / 6 位 / 30 秒；校验容忍 ±1 窗口（抗时钟漂移）。
- 密钥以 base32 文本存在 `admins.totp_secret`；**签发与校验必须共用同一套归一化**，
  否则会出现"设置成功但永远验不过"（与注册码 `EnrollCodeHash` 是同一类坑）。

*二维码（6.2 的隐藏工作量）*

前端是零依赖 + CSP `default-src 'self'`，**不能引 CDN，也不能用 `data:` URL**，
所以二维码只能在服务端生成**内联 SVG**。为此自研了 `internal/auth/qrcode.go`：

- 字节模式、ECC 等级 M、版本 1~10 自适应、固定掩码 0；
- RS 纠错在 GF(256) 上以本原多项式 0x11D 实现；格式信息 `BCH(15,5)` 异或 `0x5412`；
- 4 模块静默区；`internal/auth/qrcode_test.go` 用**内嵌参考矩阵**做逐模块回归，
  并对 20 个容量边界断言版本选择、对 214 字节断言溢出拒绝。

> ⚠️ **这个编码器曾经"能渲染但扫不出来"**，而且编译、单测、页面显示全都正常。
> 差异测试（与 python-qrcode 逐模块比对）才暴露出**五个**独立错误，全部是规范细节：
> ① `qrECCM` 表填成了"每版本数据码字总数"而非"**每块**数据码字"；
> ② 分组交错时 group-2 的块长漏了 `+1`，导致数据码字被丢；
> ③ 格式信息位序写反（必须 **LSB-first**，且两份拷贝位置不对称）；
> ④ 版本信息块的行列取反；
> ⑤ 掩码在数据**放置之后**才应用，而那时数据格已被标记 reserved 而被整片跳过。
> 现在 `init()` 会自检分块表一致性，矩阵回归测试锁死了修复后的结果。

*每日备份（6.6）*

- `VACUUM INTO` 生成在线一致快照（**不**用 cp——WAL 下会拿到撕裂副本，
  那种备份"能打开但数据不一致"，比没有备份更危险）；文件权限 0600。

  按字面执行会一次删光全部历史）；手动备份走同一口径。

*顺带修掉的一个静默缺陷（重要）*

首次在真机跑通"启动即 cleanup"时暴露：

```
level=ERROR msg=时序清理失败 err="SQL logic error: no such column: rowid (1)"
```

五张时序表建表时都是 `PRIMARY KEY(node_id, ts) WITHOUT ROWID`（让"按节点+时间范围"
直接命中聚簇 B 树），**这种表没有 `rowid` 伪列**。而 `CleanupTimeSeries` 与
`PurgeNodeHistory` 的分批删除都写了 `WHERE rowid IN (SELECT rowid ... LIMIT n)`，
于是**整个清理功能从未生效过**：过期数据一直堆积，归档节点时历史也删不干净。

它的恶劣之处在于**完全静默**——调度器只记一行 ERROR，退出码、健康检查、冒烟测试全是绿的，
症状要等磁盘涨满（几个月后）才出现。现已改为按主键 `ts` 分批，并补了 6 个回归测试
（`internal/store/store_cleanup_test.go`），断言"行确实被删掉了"而**不是**"没报错"。

> 修复过程中还踩到一个二次坑：分批推进**不能**用"上一轮删到哪"的上界 `hi`
> （`WHERE ts < cut AND ts < hi`）。因为上一轮 DELETE 已经把 `ts <= hi` 的行全删了，
> 下一轮 `ts < hi` 必然命中 0 行→`MAX(ts)` 为 NULL→循环**提前终止**，
> 12000 行只删掉 5000。正确做法是每轮重新取"剩余行里最老的 5000 行"，
> 由 DELETE 本身保证推进。

**M6 本轮实现备忘（6.8 签名 + 备份恢复演练）**

*minisign 验签（6.8）*

零依赖原则下没有用 minisign 的 Go 库（也没有官方库），而是自己解析文件格式：
`internal/auth/minisign.go` 只用标准库 `crypto/ed25519` + `golang.org/x/crypto/blake2b`。

读规范时最容易错、且**错了会拒绝所有真签名**的两点，都已用真 minisign 0.11 的对拍锁死：

1. **签名对象是 `BLAKE2b-512(文件内容)`，不是文件字节本身**（prehashed 模式）。
   写成直接对文件签名，会得到一个"看起来实现了但不认识任何真实签名"的解析器。
2. **公钥与签名文件的算法标识不同**：公钥行是 `"Ed"` → `0x6445`；
   签名行是 `"ED"` → `0x4445`（大小写不同，不是笔误）。
   一开始我把两者都当成 `0x6445`，结果对真签名报"签名无效"——
   这个消息极具误导性，会让人去怀疑密钥而不是标识。

其它已落定的格式细节：公钥 base64 解出 42 字节 = `alg(2, LE) + key_id(8) + pubkey(32)`；
签名 74 字节 = `alg(2) + key_id(8) + sig(64)`；签名的 `key_id` 必须与公钥相等；
`untrusted comment` 里显示的 key_id 是**反转**的（大端十六进制），而文件内部是小端字节。
minisign 文件第 4 行是对 `sig||trusted_comment` 的全局签名，本项目**刻意不校验**
（要校验得再实现一套 Ed25519 变体），已在代码注释里写明。

对拍结论（真 minisign 0.11 生成的真密钥与真签名）：15/15 正例接受，
覆盖 0/1/63/64/127/128/129/255/256/1000/4096 字节、UTF-8、CRLF 与无末尾换行；
3/3 反例（篡改内容 / 用错文件的签名 / 损坏签名行）判定与 minisign 一致，
且我们的报错更精确（能指出 `签名算法标识未知（0x4401，期望 0x4445）`，
而 minisign 只说 "Unsupported signature algorithm"）。

发布链路上的接入点：

- `make sign KEY=<离线私钥>` → 生成 `dist/<ver>/SHA256SUMS.minisig`；
  `make verify-sums PUB=<公钥>` → 验签 + `sha256sum -c` 双检。
- 后台设置 `install.pubkey`（两行文本，留空 = 不校验）。校验器
  `validateMinisignPubKey` **真的去解析**这把公钥（约 42 字节），
  而不是只限长度——否则管理员填错一行会得到"开了校验"的错觉，实际永远静默跳过。
- 下发的 `install.sh` 用 `__MINISIGN_PUB__` 占位，由后端
  `shellSingleQuote` 转义后注入（公钥是多行文本，直接塞进去会被 shell 当代码执行）；
  脚本里**先验签、再用 SHA256SUMS 校验二进制**，且 minisign 不存在时明确警告后继续
  （强迫所有环境都装 minisign 会把安全改进变成可用性事故）。

> ⚠️ **同一份 install.sh 有两个物理副本，本次差点因此静默失效。**
> `go:embed` 不允许 `..`，所以包目录里必须有一份拷贝：
> `scripts/install.sh`（权威）与 `internal/api/scripts/install.sh`（真正下发的）。
> 本轮只改了前者，结果**线上分发的仍是旧脚本**——本地怎么测都正常，
> 只有真去节点装才会发现验签根本没跑。已修（同步两份），并加了
> `internal/api/install_embed_test.go` 强制两者逐字节一致（不一致 `go test` 直接红）
> 与 `//go:generate` 一条命令重同步。

**M6 本轮实现备忘（6.1 源分离 / 6.3 自动 HTTPS 与 HSTS）**

*为什么自研 ACME 而不是用 `x/crypto/acme/autocert`*

三个具体理由，都不是偏好问题：

1. autocert 经 `x/net/idna` 拉进 `golang.org/x/text`，与"依赖最小化"冲突；
2. autocert **把 `identifier.type` 写死为 `"dns"`**，结构上无法签发 RFC 8738 的 **IP 证书**，
   而这正是需求里明确要的一种申请方式；
3. `golang.org/x/crypto` 里本项目只用 `argon2` 与 `blake2b`（没有引入 `acme/`、`acme/autocert/`），
   引入 autocert 需要新增依赖。

自研客户端 `internal/acme` ≈ 600 行、零第三方依赖、只用标准库（`crypto/ecdsa`、`encoding/json`、`net/http`）。

*踩过的规范细节（每一条都会让签发静默失败）*

- JWK 指纹按 **RFC 7638**：对字段名按字典序（`crv,kty,x,y`）的规范 JSON 取 SHA-256，再 base64url。
  坐标必须用 `padBigInt` 补齐成 **32 字节**——去掉前导零会得到 31 字节、生成**非法 JWK**，
  而 CA 只会回一句语焉不详的报错。
- JWS 签名是 **`R||S` 定长 32+32**，不是 `ecdsa.Sign` 给的变长 ASN.1。
- **POST-as-GET 的 payload 是空串**，不是 `e30`（那是 `{}` 的 base64url）。
- nonce 一次性，必须处理 `badNonce`：实现里做了一次自动重试并维护有界 nonce 池（≤16）。
- **下单状态机是 `pending → ready → processing → valid`**。全部授权通过后订单停在
  **`ready`**（等我们提交 CSR），只有 finalize 之后才 `processing → valid`。
  只认 `valid` 的等待循环会在第一步**死锁**——这个 bug 实际发生过，表现为测试超时。
- CSR 里**域名走 `DNSNames`、IP 走 `IPAddresses`**；`identifier` 侧则是 `{type:"ip"}`。
- `tls-alpn-01` 的挑战证书：SAN 必须**恰好等于**该 identifier，并带**标记为 critical** 的
  `id-pe-acmeIdentifier`（OID `1.3.6.1.5.5.7.1.31`）扩展，其值是
  `DER(OCTET STRING(SHA-256(keyAuthorization)))`——**漏掉外层 OCTET STRING 是最经典的失败**。
- 账户密钥与账户 URL 必须落盘（`account.key` PKCS#8 PEM 0600 + `account.url`）：
  每次重启都重新注册会撞 CA 的**按 IP 账户配额**。

*SPKI 指纹的稳定性是硬约束*

`install.spki_sha256` = 证书公钥 `RawSubjectPublicKeyInfo` 的 SHA-256（base64）。
Agent 侧证书固定用的就是它，所以：

- **续期必须复用同一把私钥**（只换证书不换密钥），否则指纹一变、**所有 Agent 同时离线**；
- 自签证书必须**复用磁盘上的产物**（用 `selfsigned.json` 记录 hosts/valid_days 判断是否需要重签），
  配置没变就不该重新生成；
- 续期时机 = `NotAfter − 有效期/3`。用**比例**而不是绝对天数，
  这样 90 天的 Let's Encrypt 与 ~6 天的短命 IP 证书都合适。

两条不变量各有专门的回归测试（`TestSelfSignedReusesKeyAcrossRestarts` 等）。

*轻量：启动绝不阻塞在网络上*

- `mode=acme` 时**首张证书在后台申请**；已缓存的证书同步加载，TLS 立即可用；
- 重试节奏：无证书 2 分钟一次，正常 12 小时一次；用 `TryLock` 串行化续期，
  避免并发下单把 CA 速率限制打满；`Retry-After` 被尊重（钳在 `[100ms, 10s]`）；
- `mode=none` / `files` 不做任何周期性检查；`files` 热加载按 mtime 做 30 秒节流，
  读失败**保留旧证书**而不是把站点打挂。

*HSTS 与 421 的两个判断*

- HSTS **只在安全连接上下发**：明文 HTTP 上发它浏览器按规范直接忽略，却会让人误以为已加固。
  它与 Secure Cookie 共用同一个 `requestSecure` 判定，因此不可能出现
  "Cookie 已降级、HSTS 还在发"的矛盾状态；伪造 `X-Forwarded-Proto` 在未配置
  `trusted_proxies` 时**无效**（冒烟里有专门的反证断言）。
- Host 不匹配用 **421 Misdirected Request** 而不是 404：这是部署配置错误，
  421 让运维立刻知道"域名对不上"，且不泄露任何内容。`ServeMux` 只看 `r.URL.Path`、
  不看 `r.Host`，所以门禁只能做成中间件。

*"本地无公网 IP、无域名"下如何验证*

- 单元测试用**内存 stub CA**（`internal/acme/stub_test.go`）跑完整流程：它真的验签、
  验一次性 nonce、验 `url`/`jwk`/`kid`、并校验 **CSR 的 SAN 与订单标识符一致**，
  因此离线就能覆盖域名 + IP 双标识、两种挑战、`badNonce` 重试、账户跨重启复用。
- JWK 指纹的期望值由 **Python 独立算出来再钉成常量**（不是"实现的输出等于实现"），
  所以字段顺序、补齐、base64 变体这类错误拦得住。
- 端到端靠冒烟脚本的第 10 节：另起一个**配了 origin 的第二实例**断言
  正确域名 200 / 错误域名 421 / 默认端口等价 / `:8443` 不等价 / ACME 路径豁免，
  以及 HSTS 只在安全连接出现。

*三种典型部署（`master.yaml`）*

```yaml
# A) 直连公网：自己申请证书（域名 + IP 可同时要）
public_listen: "0.0.0.0:443"
admin_listen:  "0.0.0.0:8443"
public_origin: "https://status.example.com"
admin_origin:  "https://admin.example.com"
tls:
  mode: acme
  acme:
    email: "ops@example.com"
    ca: "letsencrypt"                 # 先拿 letsencrypt-staging 试
    challenge: "http-01"              # 或 tls-alpn-01（无需 80 端口）
    http_addr: ":80"
    domains: ["status.example.com", "admin.example.com"]
    ips: ["203.0.113.10"]             # RFC 8738 IP 证书
  hsts: { enabled: true, max_age: 31536000, include_subdomains: false, preload: false }
```

```yaml
# B) 已有证书（商业证书 / 企业内网 CA / 其他 ACME 客户端签发的）
tls:
  mode: files
  cert_file: "/etc/ssl/probe/fullchain.pem"
  key_file:  "/etc/ssl/probe/privkey.pem"
```

```yaml
# C) 前置 Caddy/Nginx 卸载 TLS（或本机/内网调试）
tls:
  mode: none                          # 或 selfsigned（SAN 带 IP，Agent 用 SPKI 指纹固定）
trusted_proxies: ["172.16.0.0/12"]    # 只在可信代理 + X-Forwarded-Proto: https 时才认 HTTPS
```

## 附：主要风险与缓解

| 风险 | 影响 | 缓解 |
| --- | --- | --- |
| 无 Go 工具链 / 依赖拉取受限 | 无法构建 | 配置 GOPROXY 镜像；完全离线时在联网机 `go mod tidy` 后按 docs/03 §6 搬运 `GOMODCACHE`（或搬 `vendor/`，但它不入库） |
