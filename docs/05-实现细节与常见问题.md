> **两个界面的共同硬约束：卡片位置必须固定。** 卡片每 3 秒被重新赋值一次，  
> 所以任何"有值才渲染、没值就省略整行"的写法都会改变卡片高度，看起来像在跳动。  
> 做法是：DOM 按节点 id 复用（不重建）、网格行高固定、可变内容都放在固定高度的行里、  
> 缺值渲染 `—` 而不是省略、服务端排好序后前端只按序 `insertBefore`。  
> 另&#x5916;**"没有数据"不等于"0%"**——从未上报的节点必须显示 `—`，渲染 `0%` 是实打实的误读。

> **部署注意**：管理端会话 Cookie 用 `__Host-` 前缀，该前缀**强制要求 `Secure`**，  
> 而浏览器对纯 HTTP 响应会静默丢弃这条 `Set-Cookie`。代码已做成协议感知——纯 HTTP 下自动降级为  
> 不带 Secure 的 `probe_session`（能登录，但会话明文传输），因此本机调试不会被卡住；  
> **对外提供服务仍必须走 HTTPS**——可以自己终结（见下方「TLS 与证书」四种方式），  
> 也可以前置 Caddy/Nginx 卸载 TLS 并把代理网段填进 `trusted_proxies`，此时才认 `X-Forwarded-Proto: https`。  
> 注意只对**可信代理**认这个头：否则任何人都能伪造它骗到一个 Secure Cookie / HSTS。  
> 公开看板不受此限制。冒烟测试三条分支都断言（含 `X-Forwarded-Proto` 走 `__Host-` 的那条，  
> 以及"未配 `trusted_proxies` 时伪造该头拿不到 HSTS"的反证）。

## 构建约定

- 全部 `CGO_ENABLED=0` 静态编译；`-trimpath -ldflags "-s -w"`；不使用 UPX（避免杀软误报）。
- 产物命名 `probe-agent_<os>_<标签>[.exe]`，放入 `data/dist/<版本>/`，随附 `SHA256SUMS`。
  **标签必须用 `-X .../internal/dist.PlatformTag=<os>_<标签>` 注入**：`armv7`/`armv6` 在 Go 里
  都是 `GOARCH=arm`（靠 `GOARM` 区分），运行时拿不到 `GOARM`，只能构建时写死
  （Makefile、`build.ps1`、`ci-cross.sh` 三处都注入了；`probe-agent version` 会把标签打印出来）。
- `/dist/<版本>/<文件>` 是权威存放位置；`/dist/<文件>` 是**最新版本的别名**（安装脚本不知道版本号，
  取的是扁平路径）。别名只作用于单段路径，根目录若有同名文件则以显式文件为准。
- Master 不内嵌各平台 Agent 二进制，保持“Master 单二进制”。

| `cross`           | 13 平台矩阵，每平台一个 job，逐个调 `scripts/ci-cross.sh <os>/<tag>`；同一 job 里先在宿主编一次 Master          |
| `release-dry-run` | 仅 `main` 分支或手动触发：`make dist` + 校验 `SHA256SUMS` 恰好 13 行且 `sha256sum -c` 通过，产物传 artifact |

几个刻意的取舍：

- **依赖不随仓库提交**：仓库不含 `vendor/`（取舍见 `docs/03` §3.2），每个 job 显式
  `go mod download`，走默认的 `-mod=readonly`——依赖缺失时立刻报错，不会偷偷改 `go.mod`。
  因此 setup-go 的模块缓存可以放心打开（cache key 由 `go.sum` 决定，`go.sum` 一变即失效）。
  历史上曾因自带 `vendor/` 而关掉缓存并全局 `GOFLAGS=-mod=vendor`，为的是避开
  "看起来成功但没编译 vendor 里那份"的假象；现在没有 vendor，这两个顾虑都不存在了。
- **`gofmt` 只查项目代码**。命令里显式写 `./cmd ./internal` 而不写 `./...`，这样本机
  若自己执行过 `go mod vendor`，也不会把第三方代码扫进来——那儿有十余个文件
  （uuid / go-isatty / go-strftime / bigfft 等）在 `gofmt -s` 下并不规范，上游怎么发就怎么用。
- **跨平台矩阵与 Makefile 的 `PLATFORMS` 必须同步**（13 个）。`scripts/ci-cross.sh` 顶部与  
  `.github/workflows/ci.yml` 的 `matrix.platform` 都写了这条约束——armv7/armv6 是**产物命名**而非  
  GOARCH，两处不一致会造成"本地能发、CI 说不行"的割裂。

本地等价命令：`make fmt` / `make vet` / `make test` / `make test-race` / `make vulncheck` / `make dist`  
（Windows 无 make 时用 `scripts/build.ps1`，交叉编译按 Makefile 的 `dist` 逻辑手写循环，  
或直接 `bash scripts/ci-cross.sh <os>/<tag>` 逐个编）。

## 发布产物签名（minisign，6.8）

`SHA256SUMS` 只能证明"文件与清单一致"；如果攻击者控制了 `DIST_BASE` 指向的镜像，  
他可以把 `SHA256SUMS` 一起换掉，哈希校验会**全部通过**却装上投毒的二机制。  
minisign 把信任锚从"镜像 URL 可信"收敛为"这份清单出自维护者的**离线私钥**"。

```sh
# 1) 出包（离线/受控发布机）
make dist
make sign KEY=/media/usb/minisign.key     # 生成 dist/<ver>/SHA256SUMS.minisig
# 2) 上传 dist/<ver>/ 全部文件；再把公钥填进后台设置项 install.pubkey（两行文本）
# 3) 任何一台机器（不需要私钥）自检
make verify-sums PUB=/path/to/minisign.pub
```

链路两端的实现：

- 验签：`internal/auth/minisign.go`，只用标准库 `crypto/ed25519` + `golang.org/x/crypto/blake2b`，  
  零第三方 minisign 依赖（也不存在官方 Go 库）。已与真 minisign 0.11 做差分包对拍：  
  15/15 正例接受（覆盖 0/1/63/64/127/128/129/255/256/1000/4096 字节、UTF-8、CRLF、无末尾换行），  
  3/3 反例判定一致（篡改内容 / 用错文件的签名 / 损坏签名行）。
- 注入：下发的 `install.sh` 用 `__MINISIGN_PUB__` 占位，由后端 `shellSingleQuote` 转义后替换  
  （公钥是多行文本，不转义会被 shell 当代码执行）。脚本里**先验签、再用 SHA256SUMS 校验二进制**。
- 降级策略：`minisign` 不是所有系统都预装（Alpine/LXC/distroless 常缺），所以  
  **内置公钥 + 有 minisign → 强制验签、失败即中止**；**内置公钥 + 无 minisign → 明确警告后继续**；  
  **未配置公钥 → 静默跳过**。强迫所有环境都装 minisign 会把安全改进变成可用性事故。
- `install.pubkey` 的校验器**真的解析这把公钥**（约 42 字节）而不是只限长度——  
  否则管理员填错一行会得到"已开启校验"的错觉，实际永远静默跳过。

> ⚠️ 已弃用的第 4 行（对 `sig||trusted_comment` 的全局签名）**刻意不校验**，原因写在  
> `internal/auth/minisign.go` 顶部注释里：校验它需要再实现一套 Ed25519 变体，收益很低。  
> 需要防"篡改 trusted comment"的部署方请自行用 `minisign -V` 完整校验。

## 容易踩的坑（都是本项目实测踩过并修掉的）


1. **管理后台请走 HTTPS**。`__Host-probe_session` 要求 `Secure`，而浏览器对纯 HTTP 响应会  
   **静默丢弃**这条 `Set-Cookie`：服务端 200、日志正常，前端却拿不到会话、立刻被打回登录页。  
   代码已做成协议感知（纯 HTTP 下自动降级为不带 Secure 的 `probe_session`，登录能用但会话明文传输），  
   所以本机调试不会卡住；**但对外提供服务仍必须启用 TLS 或置于 HTTPS 反代之后并配好 `trusted_proxies`**。
2. **`[hidden]` 必须真正生效**（CSS 特异性陷阱）。浏览器把 `[hidden]` 实现为  
   UA 样式表里的 `[hidden] { display: none }`，特异性只有 (0,1,0)——任何作者样式里的  
   `.foo { display: flex }` 都能盖掉它，元素就"设了 hidden 却还在"。  
   本项目因此让后台**整页登不进去**：`.login-wrap` 是 `position: fixed; inset: 0; z-index: 50`  
   的全屏遮罩，覆盖层不消失，真实鼠标点击全落在遮罩上，登录按钮根本点不到  
   （会话其实早已建立，`/auth/me` 也是 200，所以从后端完全看不出问题）。  
   两个 CSS 文件顶部都用 `[hidden] { display: none !important }` 兜住了。
3. **`master.key` 必须离线备份**：它加密告警渠道凭证（Telegram bot_token 等），丢失后无法解密。  
   `init-admin` 已会顺手创建该文件，控制台会打印其路径。
4. **告警转义必须与解析模式成对下发**。Telegram 渠道支持 `HTML` / `MarkdownV2`，  
   并真的按模式做了转义（`<b>…</b>`、保留字符打反斜杠），但请求体里曾经**漏发 `parse_mode`**：  
   Telegram 按纯文本渲染，用户收到的是字面上的 `&lt;b&gt;[WARN] node#1&lt;/b&gt;` 与一堆反斜杠。  
   接口返回 200、日志全绿、后台"测试渠道"也显示成功——**只有真的盯着 Telegram 窗口才看得出**。  
   现在 `parse_mode` 随转义一起声明并做大小写归一化（后台填小写 `html` 也能用）。  
   改渠道转义时请记住：只做一半比不做更糟。
5. **重试的退避只能放在两次尝试之间**。`alert.sendWithRetry` 的循环末尾退避没有跳过最后一次，  
   三次全失败要耗 500ms + 1s + 2s = **3.5 秒**（正确是 1.5 秒）。影响被低估过：  
   `Fire` 是在调度器的**节点循环里同步调用**的，每轮每节点一次——配一个坏渠道，  
   连采集数据的调度都会被拖慢。这类缺陷任何"行为正确性"断言都发现不了，  
   必须断言**耗时**。

还有两个"看着像前端、其实在后端"的坑，改前端调不出来：

- **`nodes.status` / `nodes.last_seen` 是死列**——没有任何代码写它们。节点的真实状态只在内存运行态里，  
  所以后台列表必须用 `/api/admin/v1/nodes` 返回的 `runtime` 字段；只看库的字段，每个节点都会显示成"从未上报"。
- **Agent 的 `static` 只在进程启动后的第一次上报时携带**。Master 重启后内存运行态为空，  
  若不落库就永远补不回来（核数/内存/磁盘总量全变 `—`）。现在首次上报即落库，  
  调度器同步元数据时再回填运行态。**另外入网（`/enroll`）载荷里没有这些字段**，  
  曾经误用上报路径的写库函数把它们清零过，所以入网走的是只写环境字段的 `UpdateNodeEnv`。
- 同理，**二进制里必须内嵌 IANA 时区库**（`internal/tzdata`）：Windows 没有 `/usr/share/zoneinfo`，  
  `-trimpath` 的独立可执行文件也找不到 GOROOT 的 `zoneinfo.zip`，Alpine/distroless 更是不带 tzdata。  
  没有它 `time.LoadLocation("Asia/Shanghai")` 会失败，**整个计费保存（额度/到期/计量模式）被 400 拒掉**，  
  而 `traffic.LocalDay` 会悄悄退回 `time.Local`，"今天"的流量算错日期。
- **探测延迟曲线必须跟随后台目标启停状态**。旧实现只把数据库里查到的目标画出来，导致禁用目标后  
  历史窗口内的行仍会让它在图例里赖着不走；已改成"当前启用目标白名单"作为最终输出集，  
  只有启用的目标才能入图（`handlePublicLatency` 的 allow-list 逻辑）。
- **`LatencyTableForRange` 不能返回空表名**。`handlePublicLatency` 直接把表名拼进 `SELECT ... FROM <table> WHERE ...`，  
  `30m` 一度被映射成空字符串 → SQL 语法错 → HTTP 500。已固定映射并加空表名兜底返回空数组。
- **`DaysUntil` 已过期天数要向零截断，未到期才向上取整**。两边都用 ceil 会使"3 天前过期"显示成"已过期 4 天"，  
  平白多报一天；未到期方向保持 ceil 保证"剩 3 小时"仍显示"1 天后到期"。

再补一组"静默失效"型的坑（共同点：**不会让任何测试变红**，只会在几个月后以别的形式爆出来）：

- **`WITHOUT ROWID` 的表没有 `rowid` 伪列**。五张时序表  
  （`metrics_raw`/`metrics_1m`/`metrics_10m`/`latency_raw`/`latency_10m`）都是  
  `PRIMARY KEY(node_id, ts) WITHOUT ROWID`，而清理代码写了  
  `DELETE ... WHERE rowid IN (SELECT rowid ... LIMIT n)` → `no such column: rowid`。  
  于是**时序清理和节点历史清理从未成功过**，只往日志里写一行 ERROR。  
  清理这类"按时间/主键范围"的表要**直接用主键列**（`WHERE ts < ?`），别再碰 `rowid`。  
  更要紧的是：**分批推进不能引入"上一轮删到哪"的上界**——上一轮已经把 `ts <= 上界` 删光了，  
  再加 `ts < 上界` 条件会命中 0 行、`MAX(ts)` 返回 NULL、循环提前终止（12000 行只删掉 5000）。  
  每轮重新取"剩余行里最老的 N 行"即可，进度由 DELETE 本身保证。
- **自研编码器"能渲染"完全不代表"能用"**。TOTP 二维码因为前端零依赖 + CSP 禁 `data:`，  
  只能在服务端出内联 SVG，于是自研了 `internal/auth/qrcode.go`。它编译、单测、页面显示全对，  
  但**任何扫码器都读不出来**。必须用**独立参考实现对拍**（本项目与 python-qrcode 逐模块比对 220 组）  
  加**真实解码器回读**（`cv2.QRCodeDetector`）双重验证。  
  踩到的五个规范细节：ECC 表要填**每块**数据码字而不是每版本总数、分组交错 group-2 块长要 `+1`、  
  格式信息必须 LSB-first 且两份拷贝位置不对称、版本信息块行列别取反、掩码必须在**数据放置过程中**应用  
  （放到最后再做会因数据格已标记 reserved 而被整片跳过）。
- **备份不能靠 `cp` 数据库文件**。WAL 模式下直接拷贝会拿到**撕裂副本**——文件能打开、能查询，  
  但数据不一致。这类备份比没有备份更危险，因为它在下一次恢复演练之前看起来是成功的。  
  本项目统一走 `VACUUM INTO`（在线一致快照，且已整理过、比原文件更小），  
  并用"文件名前缀扫描"保证 Master 重启后当天不会重复备份。
- **同一份内容存在第二个副本时，必须有测试钉住两者等价**。`install.sh` 有两份：  
  `scripts/install.sh`（权威）与 `internal/api/scripts/install.sh`（`go:embed` 真正下发的）。  
  因为 `go:embed` 不允许 `..`，第二份无法避免；而第 6.8 项给权威副本加了 minisign 验签后  
  **忘了同步内嵌副本**，结果"本地怎么测都正常、节点上拿到的还是没验签的旧脚本"，  
  没有任何报错。现在 `internal/api/install_embed_test.go` 强制两份**逐字节一致**  
  （不一致 `go test` 直接红），改完用 `go generate ./internal/api/...` 一条命令重同步。  
  凡是"为了 embed/打包必须复制一份"的文件都该照此办理。
- **minisign 的公钥与签名文件用的是不同的算法标识**：公钥行 `"Ed"` → `0x6445`，  
  签名行 `"ED"` → `0x4445`（大小写不同，不是笔误）。把两者当成同一个值，  
  会让解析器**拒绝每一份真实签名**，且报错是"签名无效"——极具误导性，  
  会把排查引向密钥而无视标识。另外 minisign 签的是 **`BLAKE2b-512(文件)`** 而不是文件字节  
  （prehashed 模式）；写成直接对文件签名会得到一个"实现了但谁都不认"的解析器。  
  这两点都只能靠**与真工具对拍**发现，`internal/auth/minisign_test.go` 用的是真 minisign 0.11 的输出。
- **Agent 的上报/探测间隔必须每轮重读**。旧实现把间隔写死在启动时创建的 ticker 上，  
  于是后台把 `probe_interval_s` / `report_interval_s` 改完必须重启 Agent 才生效——看起来就是"后台设置没反应"。  
  现在每轮都在锁内重取间隔与目标清单，间隔与目标清单的改动当轮生效；同时 `d.probe` 与 `cfg` 在同一个锁内替换，  
  避免读到"新目标 + 旧探测器"而用错拨号策略。非正间隔会退回默认值（3s / 30s），否则 `time.NewTicker(0)` 直接 panic。
- **"开关关不掉"往往不是开关有 bug，而是被控对象压根没接上开关**。用户报"取消勾选内存卡片后  
  内存还是显示"：`cardOn()` 本身完全正确，也确实被调用了三处（总览汇总卡、详情页信息小卡、  
  延迟点阵）——所以从"开关机制"一路查下去都是绿的，很容易得出"复现不了"的结论。  
  真正的原因是**节点卡片区根本没有可关的抓手**：`public.cards` 当初就没为  
  节点卡的 CPU/内存/磁盘/流量/实时速率登记键，`updateCard()` 无条件渲染。  
  教训：新增一类 UI 区块时，要同时问"它属于哪个开关"，而不是只把它画出来。  
  修完顺手加了 `internal/theme/node_cards_test.go`——其中一条专门断言"键必须登记进  
  `model.PublicCardList`"，因为漏登记的表现正是"永远关不掉"。
- **画图时"没有数据"必须与"数值为 0"画出区别**。节点/Master 断联期间不落样本，  
  序列里那段就是空的；直接把相邻点连起来，会把"断联 6 小时"画成一条漂亮水平线——  
  最该被看见的故障反而最好看（与"缺值渲染 `0%`"同源）。现在两个前端都按  
  **相邻间隔中位数 ×3** 切段、段间不连线，面积与末点也按段处理。  
  阈值必须自适应：不同跨度走不同精度层（30m≈3s / 24h≈60s / 7d·30d≈600s），  
  写死秒数必然在某层上误判一头。另外**两个前端各有一份 `drawChart`**，  
  改一处等于没改——`gap_test.go` 里有一条专门做逐 token 等价断言。
- **"点了没反应"常常是"反馈在视口之外"**。系统设置页 20+ 个字段、保存按钮在最底部，  
  而保存提示是文档流里的横条、挂在 `<main>` 顶部——滚到下面改完再点保存，  
  提示出现在视口上方 2360px 处。管理员看到的是"什么都没发生"，于是反复点击。  
  请求其实每次都成功、每次都返回 204，所以**服务端日志全绿、浏览器网络面板全绿**，  
  任何后端排查都查不出问题。教训：**反馈的位置必须跟随视口而不是文档流**，  
  尤其当触发它的按钮位于长页面底部时。修法是把提示容器移出 `<main>`  
  （`<main>` 有 padding 与 `max-width`，在它内部 `left/right:0` 是相对内容盒而非视口）  
  并 `position: fixed` 钉在顶栏下方；容器 `pointer-events: none`、单条提示收回 `auto`，  
  否则这层"看不见的壳"会吃掉页面上半屏的点击（正是登录遮罩那个坑的翻版）。  
  另有两点容易漏：锚点要**实测** `topbar.offsetHeight`（顶栏 sticky + flex-wrap，  
  窄屏换行会从 48px 涨到 ~90px，写死必然在一侧算错）；`toast()` 要支持**多条共存**，  
  单条覆盖式实现里"保存成功"会被随后到达的警告顶掉，等于没提示。
- **配置项漏了中文标签，等于把内部实现细节暴露给管理员**。`backup.enabled` /  
  `backup.hour` / `backup.keep` 三项在 `SETTING_LABELS` 里没有条目，前端兜底逻辑  
  （`spec ? spec[0] : key`）直接把键名当标签渲染，还被扫进一个叫「其他」的分组。  
  更麻烦的是约束信息丢了：`hour` 是**本地时区**的 0-23、`keep` 下限 1  
  （不允许"一份都不保留"）——这些只写在 Go 的校验函数注释里，界面上完全看不到。  
  所以给设置项加键时，**必须同时补 `SETTING_LABELS` 条目与 `SETTING_GROUPS` 归属**，  
  否则它照样入库、照样生效，只是没人知道它是什么。  
  顺带一条外观契约：面向管理员的散文与悬浮提示里不该出现 `xxx.yyy` 形态的内部键名——  
  说了键名，管理员反而在设置页里找不到对应字段（那里显示的是中文）。
- **`if_data.Ibytes/Obytes` 在 32 位 FreeBSD 上是 `uint32`，64 位上是 `uint64`**。  
  同一个字段名两种底层类型：写 `ifdata.Ibytes = uint64(x)` 在 amd64 上编译通过、在 386/arm 上必失败。  
  采集器里统一按字段宽度读写（32 位内核本来就只维护 32 位计数器，会在 4 GiB 回绕）。  
  同理 `kern.boottime` 的 `tv.Sec` 在 32 位上是 `int32`，直接 `return tv.Sec` 会失败，必须显式 `int64(tv.Sec)`。  
  **改采集器后一定要跑 4 个架构的 `go vet`**：`for a in amd64 arm64 386 arm; do GOOS=freebsd GOARCH=$a go vet ./internal/agent/collector/; done`
- **不要用 `uintptr` 做指针算术**（`unsafe.Add`/`uintptr(ptr)+off`）。`go vet` 会报  
  "possible misuse of unsafe.Pointer"，而且 GC 移动对象时 uintptr 不保活。要按偏移写结构体字段，  
  先用一次 `unsafe.Pointer` 拿字节切片视图，再配合 `unsafe.Offsetof` 往切片里写。
- **macOS 不在支持范围**。darwin 会落到 `collector_stub.go`（采集全空），  
  发出去只是制造"在线但没有数据"的假节点。`Makefile` 的 `PLATFORMS` 已把 darwin 移除；  
  想重新支持，得先写 `collector_darwin.go`（sysctl / `getifaddrs` / `diskutil`）再改进矩阵。  
  同理 **mips64le 永远编译不过**——Master 依赖的 `modernc.org/sqlite` 没有该架构的生成代码  
  （`modernc.org/sqlite` 没有该架构的生成代码，缺 `sqlite3_index_constraint` 等符号），这不是配置问题而是上游限制。
- **容器里别注册系统服务**。LXC 中的 Alpine 常常没有 `/sbin/openrc`，容器内 `cat /proc/1/comm` 也不是  
  systemd/openrc-init/procd（而是 `sh`、`bash`、`tini`、`runsvdir` 等）。此时 `install.sh` 会自动加  
  `--no-service`，只把二进制放好并直接拉起前台进程。硬注册服务会让安装脚本在容器里失败退出，  
  更糟的是把 PID 1 之外的进程托管给一个根本不存在的 init。
- **Alpine/BusyBox 的 `mktemp` 不认 `-t`，`install` 命令也可能不存在**。安装脚本要用  
  `mktemp -d 2>/dev/null || mktemp -d -t probe || /tmp/probe-install.$$` 三级兜底，  
  安装动作要 `cp -f` + `chmod 0755` 兜底。`/tmp` 也可能不可写或是 tmpfs，所以要准备好绝对路径回退。
- **cgroup 限额要同时认 v1 与 v2**，而且 v1 的 `memory.limit_in_bytes` 用 `> 1<<60` 表示"不限制"  
  （直接当数值用会让节点显示 8 EiB 内存）。v2 的 `cpu.max` 是 `"quota period"` 两个微秒值、  
  写 `max` 表示不限；v1 是 `cpu.cfs_quota_us`/`cpu.cfs_period_us`，且 `-1` 表示不限。  
  换算核数时用 `quota/period` 向上取整，否则 0.5 核会被算成 0 核。
- **`MemAvailable` 在 Alpine/LXC 里常常不存在**（老内核与某些容器运行时都不导出）。  
  回落公式必须按内核文档的权威定义：`MemFree + Buffers + Cached + SReclaimable − Shmem`，  
  **不能**简单用 `MemFree`（会把缓存全算成已用，内存条常年 95%）。
- **`GlobalMemoryStatusEx` 给的是「提交（commit）」口径，不是页面文件本身**。  
  `ullTotalPageFile` = **物理内存 + 页面文件**，`ullAvailPageFile` = 剩余可提交量。  
  真机实测踩到的坑：总量按 `TotalPageFile − TotalPhys` 算（页面文件口径，2.5 GB），  
  已用却直接用 `TotalPageFile − AvailPageFile`（提交口径，含物理内存，31.9 GB）——  
  两侧基数不同，`state.Percent` 里 `if v > 10000 { v = 10000 }` 把它钳成 **100%**，  
  卡片上"交换区"永远是满格。**凡是配对的 used/total（内存、交换、磁盘）必须同基数**，  
  改一个公式就要同步改另一个。修好后本机从 100% 变成 22%（0.56 / 2.52 GiB）。  
  另外注意：**Windows 没有"实际换出到磁盘"的计数器**，这个值是提交量口径，  
  与 Linux 的 SwapUsed 不完全等价，界面上不要与 Linux 节点直接横比。
- **机器全局资源计数器不能拿来当断言**。`TestWindowsCPUTimesAdvances` 原本断言  
  "整机 idle 时间必须增长"，而 `go test ./...` 会把所有逻辑核占满（本机 12 核），  
  此时 idle 一个节拍都不涨 → **单跑必过、全量必挂**，且现场毫无头绪  
  （kernel/user 都在涨，只有 idle 不变）。实测：12 核烧满 0.8 秒，  
  `idle Δ ≈ 0.0 ms` 而 `user Δ ≈ 7828 ms`。**正确写法是主动造负载，  
  断言"自己的负载必然影响到"的那个计数器**（这里是 user），再补一条"总时间推进"兜底；  
  这类信号朝两个方向都会骗人，不能当断言目标。同风险场景：任何"等系统空闲指标变化"的  
  测试（CPU 频率、load average、电池状态）都会这样。
- **Agent 的 `static` 只在"脏标记"为真时上报**（`d.staticDirty`，首次上报后清零）。  
  这意味着**改采集器的 Static 逻辑后，已入库的旧节点不会自动更新**——  
  必须重新入网或等 Agent 重启并重置脏标记。排查"改了代码没效果"时先确认这一点，  
  别急着怀疑采集器。
- **时序查询的选层必须跟着保留期走，不能写死跨度常量**。`metrics_raw` 只保留  
  `retention.raw_hours` 小时（默认 24，可调到 1~~72）、`metrics_1m` 保留 `retention.mid_days` 天  
  （默认 7，可调 1~~30）。旧实现把 `1h/5h/24h` 硬映射到 `metrics_raw`、`7d` 硬映射到 `metrics_1m`：  
  管理员为了省磁盘把 `raw_hours` 调成 6 之后，"最近 24 小时"仍去查只剩 6 小时数据的表 ——  
  **曲线左半边凭空消失，而设置页显示一切正常**，排查时完全看不出是"保留期"与"查询层"对不上。  
  现在 `MetricsTableForRange` 按"该层保留期能否覆盖整个窗口"决定，覆盖不住就下沉到更粗的层  
  （粗粒度但连续，好过空白）。改这里要记住三点：  
  设置项常量在 `internal/store/store_traffic.go`、默认值在 `internal/api/settings.go`  
  （`settingsDefaults`）、消费方在 `cmd/probe-master/scheduler.go` 的 `cleanup`，**三处必须同步**；  
  store 不能 import api，所以默认值是各写一份的。  
  另外读设置时**必须做区间收敛**（`retentionRawHours` / `retentionMidDays`）：  
  `settings` 表就是普通 KV，绕过 API 直接写 `0` 或负数会让所有层"立刻过期"。
- **CI 的跨平台矩阵与 Makefile 的 `PLATFORMS` 是两份真相，必须同步**（当前各 13 个）。  
  `.github/workflows/ci.yml` 的 `matrix.platform`、`scripts/ci-cross.sh` 的架构映射、  
  Makefile 的 `PLATFORMS` 与 `dist` 目标里的 `armv7/armv6 → GOARCH=arm + GOARM` 分支，  
  任何一处漂移都会造成"本地能发、CI 说不行"。`release-dry-run` job 里那句  
  "SHA256SUMS 必须恰好 13 行"就是这条约束的自动护栏。  
  另：`gofmt` 检查**只显式列 `./cmd ./internal`，不写 `./...`**——  
  第三方代码里有十余个文件在 `gofmt -s` 下并不规范（uuid / go-isatty / go-strftime / bigfft 等），  
  全仓扫描会得到一个永远修不好的红灯；而且本机若自己 `go mod vendor` 过，`./...` 会把它扫进来。
