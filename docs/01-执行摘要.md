# Server Probe v3.0 —— 执行摘要（一页纸）

> 面向个人多节点 VPS 的极轻量、高安全、可插拔监控与资产管理系统。
> 本文把终稿压缩为可对齐、可交付的要点；详细规范以设计文档 v3.0 为准。

## 一句话概括

**Agent 只外呼、不监听；Master 只被动接收、从不下发命令。** 因此系统在架构层面不存在远程控制通道，
RCE 与横向控制的风险被结构性排除，安全设计只需收敛在三个方向：**展示层、计量正确性、监控者自身的可用性**。

## 1. 设计哲学（四条主线）

| 主线 | 含义 | 落地方式 |
| --- | --- | --- |
| 零入站攻击面 | Agent 不监听任何端口 | 纯外联；防火墙可全阻断入站 |
| 纯被动拉取 | Master 绝不主动连 Agent | 配置变化只能由 Agent 在出站请求中获取；**无远程卸载/远程命令** |
| 展示与管理隔离 | 公开页与后台权限解耦 | 公开 API 使用独立 DTO（字段白名单），模型中根本没有 IP/令牌/价格 |
| 单文件零依赖 | 全 Go，可静态编译 | Master 内嵌 SQLite（`modernc.org/sqlite`）与默认主题；Agent 无运行时依赖 |

## 2. 拓扑与通信

```
外部目标(三网/公网/自定义) ← TCP 握手 / ICMP Echo
        ▲
   Agent（多节点，零监听）
        │ POST /report    （HTTPS + Bearer，每节点独立令牌）
        │ GET  /config    （仅 config_version 变化时）
        ▼
   Master（内存运行态 · 写入管线 · 状态机 · 计费 · 告警 · SQLite WAL）
        ├── 公开看板 API + 主题引擎
        └── 管理后台 API
```

## 3. 关键机制速查

| 主题 | 结论 |
| --- | --- |
| 上报 | 默认 3 秒一次；失败指数退避（≤60s），本地缓存最近 100 条按 `ts` 升序补报；401/403 退避 10 分钟且**不自毁** |
| 存储 | 最新状态**只存内存**；落盘的是聚合结果。写入时同步生成三层（10s/1m/10m），过期直接删除，无事后降采样 |
| 实时层 | 30 分钟环形缓冲（≈600 点 @3s，约 60 KB/节点），不落盘 |
| 保留 | 高精度 24h · 中精度 7d · 低精度 30d（可配 1~365）；清理每小时分批 DELETE |
| 离线判定 | `max(30s, 10×上报间隔)` → 先“疑似离线”，再过 30s 确认窗口才转 `offline`；Master 重启有 2×超时宽限期 |
| 探测 | 每目标可选 TCP / ICMP；周期 ≥10s、每目标每轮 ≤5 次、总数 ≤30；**拨号层**拒绝私网/回环（防 DNS 重绑定） |
| 流量 | **按网卡分别求差**（修复 A1）；`boot_time` 变化判重启，32 位计数器判回绕；基线 ≤60s 落盘（A8） |
| config_version | 该节点**有效配置**的规范化 JSON 摘要（SHA-256 前 8 字节）；只有受影响的节点会重拉 |
| 探测目标 | `host/port/method` **不可原地修改**，改即新建并停用旧目标（避免历史曲线混入不可比数据） |
| 令牌 | 256 位随机 `pk_` 前缀；库内只存 SHA-256；常量时间比较；同节点新令牌首次使用后旧令牌自动失效 |
| 注册码 | 一次性、30 分钟、只存哈希、绑定节点；**带条件的 UPDATE 原子消费**并检查受影响行数（防并发双花） |
| 告警 | 离线/探测失败需连续 N 次确认（3）；指标需持续 5 分钟；每 `(节点,事件类型)` 独立冷却（60 分钟）；恢复通知不受冷却 |
| 存储预算 | 默认 ≈3~4 MB/节点；50 节点 Master 内存 ≤64 MB |

## 4. 安全要点（评审后）

| 编号 | 要点 |
| --- | --- |
| S1 | 节点上报字符串入库前按白名单+长度清洗；输出端转义；邮件主题去 CR/LF；前端只用 `textContent` |
| S2 | 公开站与管理端**默认分离为不同源**；管理 Cookie 用 `__Host-` 前缀；写请求必须带 `X-CSRF-Token` |
| S3 | 自签证书固定**公钥(SPKI)指纹**而非整张证书，支持多指纹并存以平滑轮换 |
| S4 | 拨号层逐个校验解析结果并拒绝内网/回环/链路本地/云元数据地址 |
| S5 | 仅当连接来源命中 `trusted_proxies` 时才信任 `X-Forwarded-For`；直连时保持为空 |
| S6 | 注册码消费与令牌重签发用原子 UPDATE + RowsAffected 检查 |
| S7 | 拒绝 `http://` 的 Master 地址；仅本机回环可用 `--insecure-http` 放行 |
| S8 | `install.master_url` 严格校验为 https 且字符集受限；注册码用 Crockford base32；命令参数一律加引号 |
| S9 | `ReadHeaderTimeout/IdleTimeout`、请求体上限、每 IP 并发/频率上限；公开数据由内存快照提供 |
| S10 | `dist` 建议外置并离线签名 `SHA256SUMS`，公钥带外配置 |
| S13 | `data_dir` 0700、`probe.db`/`master.key` 0600；卸载只删安装清单记录的路径 |

**残余风险（架构上无法杜绝）**：Master 被入侵可篡改展示数据（`dist` 由 Master 提供时还会污染新装 Agent）；
被入侵的节点可上报虚假指标；管理员浏览器被入侵不在设计范围内；单进程单 SQLite 仅适合 ≈50 节点以内。

| 指标 | 目标 |

| Master 内存 | 50 节点 ≤64 MB |
| 数据库体积 | 默认 ≈3~4 MB/节点 |

## 6. 上线前检查清单

- [ ] 公开站与管理端分离为不同源，或管理端限制 IP
      （已支持：配 `public_origin`/`admin_origin`，或用 `public_hosts`/`admin_hosts` 显式覆盖；

- [ ] 已启用 TOTP，并保存恢复码
- [ ] 终结 TLS 并启用 HSTS；自签证书场景已配置 SPKI 指纹
      （已支持：`tls.mode` 四选一 —— `none` 交给前置反代 / `files` 自带证书（热加载）/
      `selfsigned` 自签（SAN 含 IP）/ `acme` 自动申请（域名证书 + RFC 8738 IP 证书）；
      HSTS 只在安全连接上下发；`GET /api/admin/v1/tls/status` 可看 SAN / 到期 / SPKI 指纹）
- [ ] `trusted_proxies` 配置正确（直连时保持为空）。它决定服务端是否采信 `X-Forwarded-Proto: https`，
      也就是决定会话 Cookie 用 `__Host-`+Secure 还是降级——配错要么把自己锁在门外，要么白降安全等级
- [ ] 确认部署形态下的会话 Cookie 名与预期一致：HTTPS/可信反代应为 `__Host-probe_session`，
      纯 HTTP 下会是 `probe_session`（能用但明文传输）
- [ ] `install.mode` 保持 `on_demand`，`install.master_url` 已校验
- [ ] 已配置外部心跳 `heartbeat_url`，并确认能收到失联通知
- [ ] 数据目录 0700、`master.key` 0600，且密钥与备份分开存放
- [x] 做过一次备份恢复演练（`scripts/restore-drill.sh` / `make restore-drill`，35 项通过）
- [x] CI 中 `govulncheck` 通过，发布产物已签名（`make sign` + `install.pubkey` 校验，见 6.8）

### 本轮（第 119~123 项）：接通「探测连续失败」告警 · 补齐 Agent 侧测试

#### 1. `alert.KindProbeFail` 此前是一条"只有壳没有芯"的规则

数据库 `CHECK` 白名单、`DefaultRules()`、API、后台标签（「探测连续失败」）全都到位，
唯独**没有任何代码发出这个事件**——一条永远沉默的规则比没有这条规则更糟，
因为管理员会以为"配好了"。

它要表达的那类故障无法被现有两类告警覆盖：

| 异常类别 | 判定依据 | 覆盖不到的 |
| --- | --- | --- |
| 节点离线 | `LastSeen` 过期 | 节点在正常上报，只是探测目标不通 |
| 资源异常 | cpu / mem / disk 阈值 | 与探测结果无关 |
| **探测连续失败** | 目标连续 N 轮不通 | （本轮补齐） |

接通时按四条口径收口：

* **权限/策略类错误不算失败**。`icmp_not_permitted`（无 raw socket 权限，容器与低权限
  服务账号很常见）与 `blocked_target`（S4 拨号层拦下内网/回环/云元数据地址）
  的语义是"**没测成**"而不是"**测到了不通**"。算进去会让所有无特权节点永远在报警，
  而那种告警是真的在报，管理员无法与真故障区分。反过来 `refused` 必须算失败——
  TCP 端口上服务没了，正是最该被看见的故障。
* **粒度挂在目标上**，state 键是 `probe_fail:<target_id>`。若用节点级基础键，
  两个目标各失败两次就等于"连续 4 次"，`ConfirmN=3` 提前一轮触发。
* **"目标本轮没上报"不等于"恢复"**。只遍历上报里出现过的目标，
  于是空探测天然不触发任何 `Clear`；反之，任何"按库里的目标清单去判、
  不在清单里就当恢复"的写法都会把每一次上报间隙当成恢复，连续计数永远清不到头。
* **按轮去重**（见下）。

#### 2. 「按轮去重」——这条链路真正的坑

Agent 每 `probe_interval_s`（默认 30 秒）才探一轮，而调度器的 `alertTick` 每 10 秒扫一次；
`LatestLatency` 又是**持久的**（`applySample` 只在拿到非空结果时整体替换），
所以同一轮的失败样本会被反复扫到 3 次以上。若每次扫描都记一笔，
默认 `ConfirmN=3` 会在**一轮之内**（30 秒）被满足——
"连续 3 轮确认"静默退化成"失败一次即告警"，看起来功能完全正常。

修法：新增单调递增的 `state.NodeRuntime.LatencyRound`（在替换样本的**同一次** `Update` 里
自增），加一张 `Scheduler.probeRounds` 去重表，键为 `(node, target)`。

* 选**轮次号**而不是时间戳：时钟跳变、以及"同一秒内的两轮"都不会干扰判定。
* 判重用 `==` 而不是 `<=`：轮次号在单进程内单调，等号已经够用；万一遇到异常回退，
  宁可多计一次（告警偏早）也不要永远计不上（告警永不触发）。
* 去重表由 `pruneProbeRounds` 按当前运行态裁剪，不会随"建过又删掉的目标"无限增长。

新增 `cmd/probe-master/probe_fail_test.go`（10 例 / 457 行），刻意使用**真实的**
`store.Repo` + `state.Registry` + `alert.Engine` 而不是替身——
这一组缺陷的性质就是"谁和谁共用一个计数器"，而替身恰好会把最关键的那个共享关系抽象掉。
覆盖：按轮不按扫描、逐目标不逐节点、state 键逐目标、权限/策略类错误一律不计、
五类真实失败各计一次、空探测不清零、恢复只发一次且计数归零、规则停用后彻底安静、

#### 为什么自升级不复用公开的 `/dist/`

`install.mode` 默认是 `on_demand`：只有"存在未使用的注册码"时才开放 `/dist/`。
节点装好之后注册码就被消费了，那条路随即关闭——**照它的语义这是对的**
（不该长期匿名分发二进制），但升级会被一起关死。

所以升级走 **agent 作用域**：一个已注册节点随时可以取自己平台的构件。
既不需要长期开放匿名分发，也不用把注册码的语义改成"没用完就一直开着"。

#### 三条不可让步的规则（写在 `updater.go` 的包注释里）

* **先校验后落地**：下载到同目录的 `<目标>.new`，SHA-256 对上才改名。
  校验通过前目标路径上不会出现任何内容——中途崩溃不会留下"看着像完成、实际是坏的"二进制。
* **绝不主动降级**："比最新还新"也算无需动作（Master 回滚版本时不能把全网一起拖下去），
  降级只能由运维显式 `--version`。
* **替换失败必须还原**：改名失败就把备份换回来，不留"目标缺失 + 有 `.new`"的半套状态。

#### 发布标签为什么要"注入"而不是"运行时推断"

产物名的第 2 段是**标签**而不是 `GOARCH`：`armv7`/`armv6` 在 Go 里都是 `GOARCH=arm`
（靠 `GOARM` 区分），而运行时**拿不到** `GOARM`。猜错就会下载一个跑不起来的二进制，
所以标签在构建时用 `-X .../internal/dist.PlatformTag=<os>_<标签>` 写死
（Makefile、`scripts/build.ps1`、`scripts/ci-cross.sh` 三处都注入了）。
没注入时退回 `GOOS_GOARCH`，于是 32 位 ARM 会去要 `probe-agent_linux_arm`
——发布矩阵里没有这个名字，服务端如实回"该平台未发布此版本"，而不是装上一个错的。

`probe-agent version` 会把标签一并打印出来（`(发布标签 linux_armv7)`）：这是运维**唯一**
能一眼看出"手上这份是发布构建还是随手 `go build` 的"的地方。

#### 本轮新增的端到端覆盖：冒烟第 8.6 节

自升级这种链路最怕"测了一遍假的"：拿同一份二进制改个名当新版本，什么也测不出来。
所以冒烟里**真编了两份不同版本号的 Agent（1.0.0 与 9.9.9）**，然后：
发布 → 版本发现 → 取件校验 → 实际升级 → 备份 → 再查（已是最新）→ 回滚，
每一步都断言。还顺带覆盖了两个静默面：非点分目录（`nightly-*`）必须被忽略，
以及未发布的平台要能报"该平台没发"而不是"Master 没配好"。

### 本轮（第 139~143 项）：公开看板与后台——两个域名，还是一个站点

需求是一句话：「公开看板和管理后台**可设置**是否分离成两个域名，或者不分离只在一个站点下访问」。
难点全在"**可设置**"三个字上，因为它同时约束了三件事：开关放在哪、改完什么时候生效、
以及**配错了会怎样**。

**开关放在哪。** 三条候选各有一个致命的短板：放进 `master.yaml` 的话，改一次要重启
——而"登录后台改一下"才是管理员预期的方式；只做成设置项的话，`admin_listen`
（管理端监听地址）这种真的需要重启的东西会被一起误当成可以热改；
做成纯前端开关则完全落空，域名白名单是服务端行为。最后落成**两层**：
`master.yaml` 的 `public_hosts` / `admin_hosts` 是**启动基线**，后台的
`site.public_hosts` / `site.admin_hosts` 非空时**顶替**它（不是并集——并集会让
"后台里删掉的域名依然放行"，又是一种看不见的失效），形态本身由 `site.layout`
三选一：`auto`（跟随配置文件）/ `single`（同站，一个域名）/ `split`（分离，两个域名）。

**"一个端口 + 两个域名"必须能表达。** 这是本轮最关键的一个判断：分离靠的是 **Host**，
不是监听地址。反代把两个域名都转到同一个端口、由 Master 按 `Host` 判断该服务谁，
是完全正常的部署形态——若把门控写成"按入口判域名"，这种部署下后台在公开域名上
就能打开，等于没有分离。所以门控是**按路径**做的：`/`、`/api/public/*` 走公开域名，
`/admin/`、`/api/admin/*` 走管理域名（`isAdminPath` 用精确前缀，不用"含 admin"这种模糊判据——
那会把 `/administrator` 也算进来）。

**"改完即时生效"必须是真的。** 门控是在进程启动时装配的，而形态是运行时设置。
把清单读成闭包变量，"即时生效"就是假的：界面显示已分离、实际仍在放行，且没有任何报错。
这一条钉死在 `TestSiteGateReadsSettingsPerRequest` 上——**门控只构造一次**，之后改设置，
行为必须跟着变；另配一条"把清单冻结在构造时"的变异。这个形态**单元测试一开始没抓到**
（测试里门控是就地构造的），是端到端冒烟第 10b 节跑出来的。

**配错的方向是不对称的。** 配宽了 = 公开域名能打开后台；配窄了 = 管理员被锁在自己
后台外面，而**改回来恰好需要访问后台**。所以后者必须在写入前拦掉：
`split` 却缺任一域名清单时，保存直接 400 拒绝，报错里说清"否则管理后台会因为域名不匹配
而无法访问"。请求侧同样兜一层（`split` + 无管理域名时管理路径一律 421），
两道合起来才是"不可能自锁"。

**默认值只能是 `auto`。** 存量部署并没有"表态"过要分离还是同站，
用一个新默认值去重新解释它们的既有配置，就是一次静默的行为变更。
这条同时意味着 `auto` + 未配管理域名时管理路径**必须放行**，否则升级之后
所有单域名实例的后台集体打不开。

前端这一侧只做了一件事：在设置页新增「站点形态」分组（下拉框 + 两份多行域名清单），
但配了一条能挡住"漂移"的护栏——`TestSiteLayoutOptionsMatchBackendValues`
直接把 `admin.js` 里的选项串用正则取出来，与 Go 侧的 `siteLayoutValues` 比对：
少一个取值就是"某个合法形态在界面上根本选不出来"，管理员会以为它不存在。

部署文档这侧新增 `docs/04` §2.5（同站/分离/跟随配置文件三态对照、两个域名共享一个端口的
Caddy 反代样例、为什么是 421 而不是 404、ACME 挑战豁免、明文 HTTP 直连 IP 的警告），
故障排查表补了四条（`421 · 域名不匹配` 附带可直接复现的 `curl` 命令、分离保存被拒、
"改了域名清单但行为没变"），上线清单里把 Host 一条拆成"分离验两个方向 / 同站验两个路径"。

写这一轮又挖出 3 个真缺陷（`docs/01` 缺陷 52~54），其中两个是**这一轮自己引入或自己漏掉的**：

### 已修缺陷清单（按发现顺序）

1. 聚合环节的缺陷导致数据全废。编译期无法发现，仅因补了聚合测试才暴露。
2. 聚合桶用 `start == 0` 当“未初始化”哨兵，而 0 是合法桶起点（与 epoch 对齐的第一个窗口），
   导致首个窗口每来一个样本就误判跨桶、凭空多出若干行。
3. 内存运行态是 Agent 首次上报时才惰性创建的，而名称 / 分组 / `public_visible` 谁都没有写入过——
   结果**公开看板永远为空、公开节点详情永远 404**。已补 `Registry.SyncMeta` 与调度器周期性元数据同步，
   并保证“同步元数据”不会被误当作“已上报”（否则新建节点会在 30 秒后被误报离线）。
4. PATCH 节点用 `Registry.Update`，对从未上报的节点静默失败 → 公开可见性改动丢失。
5. `init-admin` 不创建 `master.key`，配置路径不可写要到第一次启动才暴露；现已提前创建并提示备份。
6. 管理端会话 Cookie 最初无条件下发 `__Host-` + `Secure`。该前缀**强制要求 `Secure`**，
   浏览器对纯 HTTP 响应会**静默丢弃**这条 `Set-Cookie`：服务端 200、日志正常，前端却拿不到会话、
   立刻被打回登录页，表现为"登录成功却立刻退出"。已改成协议感知下发
   （本机 TLS / `tls.mode=files|acme` / 可信代理 + `X-Forwarded-Proto: https` 才用 `__Host-`，
   否则降级为不带 Secure 的 `probe_session`）。注意只对**可信代理**认那个头，否则谁都能伪造。
7. **注册流程整体不可用（阻塞级）**：注册码入库时哈希的是“去分隔符并大写”后的形式，
   而核验时直接哈希请求原文；注册码本身一定形如 `ABCD-EFGH-JKLM`（带两个 `-`），
   于是**任何注册码都无法通过校验**，节点永远注册不上。已抽出 `auth.EnrollCodeHash` 作为
   签发/核验的唯一入口，并补了“两侧哈希必须一致 + 对分隔符/大小写/空白不敏感”的回归测试。
   这个缺陷编译期与单元测试都查不出来，是**端到端冒烟测试**（真实走完 enroll → report）才暴露的。
8. **后台整页登不进去（阻塞级，且"后端完全看不出问题"）**：`.login-wrap` 是
   `position: fixed; inset: 0; z-index: 50` 的全屏遮罩，而它声明的 `display: flex`
   **特异性高于浏览器默认的 `[hidden] { display: none }`**，于是 `#login` 与 `#password-modal`
   即使带 `hidden` 也照样渲染成覆盖层。真实鼠标点击全落在遮罩上，登录按钮根本点不到；
   而 `#login-error` 是空的、`/auth/login` 用 curl 调是 200、会话 Cookie 也正常签发——
   从服务端到接口全都是绿的，只有"真人在浏览器里点一下"才会暴露。
   两个 CSS 文件顶部已用 `[hidden] { display: none !important }` 兜住，并补了浏览器实测。
9. **入网清零资源规格**：`/api/agent/v1/enroll` 的载荷里只有 hostname/os/arch/virt 等环境字段，

   cpu_cores / mem_total / disk_total / kernel / cpu_model 写成 0**。现象是"节点在线、
   卡片显示 0 核 / 0 B 总量"，而且 Agent 不重启就补不回来（`static` 只在进程启动后的第一次上报携带）。
   已抽出只写环境字段的 `store.UpdateNodeEnv`，并补了"资源规格必须原封不动"的单元测试
   与端到端断言。
10. **缺少 IANA 时区库，计费保存整体失效**：Windows 没有 `/usr/share/zoneinfo`，
    `-trimpath` 的独立可执行文件找不到 GOROOT 的 `zoneinfo.zip`，Alpine/distroless 不带 tzdata——
    `time.LoadLocation("Asia/Shanghai")` 一律失败，`PUT /billing` 直接 400。

   同时 `traffic.LocalDay` 会悄悄退回 `time.Local`，"今天"的流量算错日期。
   已内嵌 `internal/tzdata`（Master 约 +400 KB，Agent 不受影响），
   并在冒烟测试里加了"合法时区 204 / 非法时区 400"的双向断言。
11. **`nodes.status` / `nodes.last_seen` 是死列**（没有任何代码写它们）。节点的真实状态只在内存运行态里，

    里合并运行态（一次遍历，不做 N+1），后台状态胶囊改从 `/runtime` 取。
12. **静态信息跨 Master 重启永久丢失**：`static` 只在 Agent 进程启动后的第一次上报携带，

    调度器同步元数据时再回填运行态（只填空值，不覆盖 Agent 刚报的新值）。
13. **状态机有死循环态**：节点进入 `warning` 后再也回不到 `online`（判断条件写成了

14. **"没有数据"被渲染成 `0%`**：从未上报的节点在卡片上显示 `0%`，而 `0%` 的语义是
    "测到了，使用率为零"——这是实打实的误读，已统一渲染为 `—`。
15. **`LatencyTableForRange("30m")` 返回空表名导致公开延迟 500**：`handlePublicLatency` 把表名直接拼进 SQL（`SELECT ... FROM <table> WHERE ...`），旧映射让 `30m` 返回 `""` → SQL 语法错误 → HTTP 500。已固定映射到 `latency_raw` 并加空表名兜底（返回空数组而非 500）。
16. **禁用探测目标后仍在公开曲线图例里赖着不走**：旧实现只把查询窗口里出现过的目标画出来，禁用后历史数据仍在，图例看起来"改配置没反应"。已改为以"当前启用目标"为白名单，只有启用的目标才入图；数据库残留行仅用于填充已启用目标的曲线点。
17. **已过期天数多算一天**：`DaysUntil` 曾对正负 diff 统一用 ceil，使"3 天前过期"显示成"已过期 4 天"。已改为未到期方向 ceil、已过期方向向零截断，两侧语义独立且符合直觉。
18. **月费合计直接相加导致年付/终身节点失真**：`price_minor` 是单次支付周期的金额，旧代码直接求和让年付节点贡献 12 倍、终身节点贡献全款。新增 `model.MonthlyEquivalent` 按周期折算，并补了 `roundDiv` 避免小金额被截断为 0；后台节点页新增同口径卡片与公开看板对齐。
19. **Agent 的上报/探测间隔改完不生效（数据竞争 + 死间隔）**：`Run` 与 `probeLoop` 都在启动时用 `d.cfg.*IntervalS` 建好 ticker，之后只在重试路径里 `Reset`，所以后台把间隔改掉必须重启 Agent；更糟的是 `d.cfg` 在这些位置是**无锁读**，与 `syncConfig` 的锁内写构成数据竞争，`d.probe` 也被替换于锁外，可能读到“新目标清单 + 旧探测器”从而用错拨号策略。已改为每轮在锁内重取间隔/目标/探测器，非正间隔退回默认值（`time.NewTicker(0)` 会 panic）。
20. **二维码"能渲染但扫不出来"（自研编码器，五个规范细节错误）**：TOTP 二维码必须内联 SVG

   页面显示正常，但**没有任何扫码器能读出内容**——直到与 python-qrcode 做逐模块差异比对才暴露。
   五个独立错误：① `qrECCM` 表填成"每版本数据码字总数"而非"**每块**数据码字"；
   ② 分组交错漏了 group-2 的块长 `+1`，数据码字被丢；③ 格式信息位序写反（须 LSB-first 且两份拷贝位置不对称）；
   ④ 版本信息块行列取反；⑤ 掩码在数据放置**之后**才应用，此时数据格已标记 reserved 而被整片跳过。

21. **时序清理从未生效（静默失效，且无任何测试）**：五张时序表建表时是
   `PRIMARY KEY(node_id, ts) WITHOUT ROWID`，**没有 `rowid` 伪列**；而 `CleanupTimeSeries` 与
   `PurgeNodeHistory` 的分批删除都写了 `WHERE rowid IN (SELECT rowid ... LIMIT n)`，
   于是一次都没成功过：过期时序数据一直堆积，归档节点时历史也删不干净。
   `SQL logic error: no such column: rowid` 只被记成一行 ERROR 日志——
   退出码、健康检查、冒烟测试全绿，症状要等磁盘涨满（几个月后）才显现。
   已改为按主键 `ts` 分批，并补 6 个回归测试，断言"行**确实被删掉**"而非"没报错"。
   修复中又踩到二次坑：分批推进**不能**用"上一轮删到哪"的上界 `hi`，
   因为上一轮 DELETE 已把 `ts <= hi` 的行删光，下一轮 `ts < hi` 命中 0 行 → `MAX(ts)` 为 NULL →
   循环**提前终止**（12000 行只删掉 5000，测试 `TestCleanupTimeSeriesLargeBatch` 精确复现）。
   正解是每轮重新取"剩余行里最老的 5000 行"，由 DELETE 本身保证推进。
22. **`install.sh` 有两份物理副本，改了一份导致"线上发的还是旧脚本"（静默失效）**：

   与 `//go:generate cp` 一条命令重同步。教训：任何"同一内容的第二个副本"都必须有测试钉住等价性。
23. **minisign 公钥与签名文件的算法标识不同，误当相同会拒绝所有真签名**：
   公钥行是 `"Ed"` → `0x6445`，签名行是 `"ED"` → `0x4445`（大小写不同，不是笔误）。
   一开始两者都按 `0x6445` 解析，对真签名报"签名无效"——这条错误极具误导性，
   会把排查引向密钥而忽略标识本身。已拆成两个常量并加 `TestMinisignSignatureAlgDiffersFromPublicKey` 锁定。
   另一处同类陷阱：minisign 签名的是 **`BLAKE2b-512(文件)`** 而非文件字节（prehashed 模式），
   写成直接对文件签名会得到一个"实现了但谁都不认"的解析器。
24. **节点卡片上的指标没有开关，`public.cards` 关不掉（"开关关不掉"）**：
    `public.cards` 当初只登记了三类卡片键——总览汇总卡（`kpi_*`）、详情页信息小卡（`info_*`）、
   节点卡的延迟点阵（`lat_bars`）。而**列表页每张节点卡片内部的 CPU / 内存 / 磁盘 / 流量
    四条进度条与底部实时速率行根本没有对应的键**，`makeCard` 造出这些 DOM、`updateCard`
    无条件填值与显示。于是管理员在「系统设置 → 公开看板」取消勾选 `info_mem` 之后，
    详情页那格确实消失了，列表页每张卡片上的「内存」进度条却**照样显示**——
    用户报的就是这一条。
    特别难查的一点：`cardOn()` 本身是对的，也确实被调用了三处（总览卡、详情小卡、延迟点阵），

33. **告警重试在最后一次失败后还退避一轮**（补测试时发现）。`sendWithRetry` 的循环是
    "发送失败 → 退避 → 重试"，但退避被放在了循环末尾、没有跳过最后一次，于是三次全失败要
    耗时 500ms + 1s + 2s = **3.5 秒**（正确值是 1.5 秒）。退避的唯一作用是把相邻两次尝试错开，
    最后一次之后已经无事可做。影响面被低估过：`Fire` 是在调度器的**节点循环里同步调用**的，
    每轮每节点一次——配了一个坏的告警渠道，连采集数据的调度都会被拖慢。
    这个缺陷所有既有测试都发现不了，只有"断言耗时"的用例能抓住。
34. **两个"测试通过了错误原因"的用例**（变异验证发现，见上一节）。坏库检测最初断言
    "错误必须来自 `quick_check`"，但把 `quick_check` 整段删掉后测试**依然绿**——
    因为 `Open` 的 DSN 带 `auto_vacuum(INCREMENTAL)`，建连时就读了指针映射页，
    页损坏总在 `Ping` 阶段先暴露，那行代码永远轮不到执行；假 Store 的 `MarkDelivered`
    又只记录"被调用过"、没真的把 `delivered` 置位，导致"是否送达"的断言是空断言。
    两者都证明：**测试全绿不等于被测代码被覆盖**，变异验证是必需品而不是形式。

35. **`TestWindowsCPUTimesAdvances` 断言了"整机 idle 必须增长"，导致全量测试偶发失败**（第 96~97 项之后回归检查时第二次撞上，才定位到根因）。该测试原本轮询最多 2 秒、等
    `idle`/`kernel`/`user` 三项同时推进；但 `go test ./...` 会让各包并行编译+运行，
    **把 12 个逻辑核彻底占满**，此时 idle 时间一个节拍都不增长——失败现场正是
    `kernel`/`user` 都在涨、只有 `idle` 一条不变。上一轮把它归因于"系统时钟节拍（空闲时会拉长）"
    并改成"多轮询几次"，方向是错的：**轮询再久也等不到一个物理上不会增长的数字**。
    实测（12 核，进程内烧满 12 个 goroutine 共 0.8 秒）：`idle Δ ≈ 0.0 ms`、
    `kernel Δ ≈ 1906 ms`、`user Δ ≈ 7828 ms`。
    它单跑能过，只是因为启动斜坡会漏进一两个 tick —— 所以这条断言**朝两个方向都会骗人**
    （单跑假绿、全量假红），连"改回依赖 idle"的变异都测不出来（变异版单跑照样绿）。
    已改为**主动造负载**并断言 `user` 必须增长（秒级、数千万个单位，与机器忙不闲无关），
    外加"总时间必须推进"作为计数器活着的最低证据，并用原子计数自证"负载真的造出来了"
    （这条自检本身也有变异覆盖）。产品侧变异改为"让 `systemTimes` 恒返回零值"，
    两条均变红。**教训：机器全局资源计数器（idle）不能当作断言目标，
    要用"自己造的负载必然影响到的那个计数器"。**

36. **ICMP 探测在回退路径上 100% 失败（`invalid argument`）**。
    这是本轮（补 `prober` 单测时）发现的**最严重**缺陷。
    `icmp.ListenPacket("udp4", …)` 在部分平台上会失败
    （实测本机报 "The requested protocol has not been configured into the system"），
    代码于是回退到 `"ip4:icmp"` 原始套接字——但**目标地址仍是按 `udp4` 造的**
    `*net.UDPAddr`。两种套接字返回的 conn 期望的地址类型不同：
    `udp4` 要 `*net.UDPAddr`，`ip4:icmp` 要 `*net.IPAddr`；
    `WriteTo` 类型不匹配时**每一次都返回 `invalid argument`**。
    实测：用 `&net.UDPAddr{}` 写永远失败；换成 `&net.IPAddr{}` 立刻 `n=13`、
    收到 echo reply、耗时 0。Windows 与 FreeBSD 都会走到这条回退分支，
    也就是说这两个平台上的 ICMP 探测**从来没有成功过一次**。
    它之所以能活到补测试这一步，是因为失败被归成了 `timeout`/`other`：
    看板上表现为"这些节点的目标一直不通"，而网络其实完全正常——
    与缺陷 32/33 是同一种"看起来在工作、实际全错"的形态。
    修复 = 目标地址类型与所选套接字**成对**决定；并用
    `TestProbeICMPNeverReportsAFalseFailure` 把合法结果限定为「成功」或
    `icmp_not_permitted` 两种，任何其它错误一律判红。
    **这条护栏的意义不是"测出 ICMP 能通"（那依赖环境），
    而是"绝不允许把它自己没测成的结果报成目标故障"。**

37. **EPERM 的文本是 "operation not permitted"，不是 "permission"**。
    `classifyErr` 只匹配 `"permission"`，而原始套接字被拒时 Go 给出的信息里
    **没有**这个词（是 `permitted`）。于是"没有 raw socket 权限"被归类成 `other`——
    一个笼统到无法据以行动的错误码：既不能让节点被识别为"无特权"，
    也让探测失败告警的权限豁免（与缺陷 36 同轮设计）失去判据。
    修复 = 一并匹配 `"not permitted"`，并补 11 条真实 errno 文本的真值表断言。

38. **`no route to host` 报成「域名解析失败」，同一故障跨平台两种结论**。
    旧实现把它与 `"no such host"` 归进同一分支，于是这个与域名毫无关系
    （DNS 早就返回了）的错误被贴上 `dns_failed`；而在 Windows 上，
    同类故障的文本里含 `unreachable`，因而报成「不可达」。
    同一张看板上，管理员对同一个故障看到两种标签、拿到两种处置建议——
    这正是"错误码是给人看的"这一条被破坏后的典型后果。
    修复 = `no route to host` 明确归入 `unreachable`，并把
    `unreachable` / `no route to host` / `network is down` 一起钉进真值表。

39. **`min == 0` 哨兵吃掉了合法的 0 微秒样本，导致 `min > avg`**。
    TCP 握手打**回环地址**时确实会测出 0 微秒，而旧实现用"`min == 0` 表示还没赋值"
    来判断首个成功样本，于是那一次结果被丢弃。随后 514、584 进来，
    min 停在 514、avg 却是 366——**最小值大于平均值**，一组自相矛盾的数字。
    修复 = 用独立的 `ok` 计数判断"是不是首个成功样本"，而不是拿 min 的数值当哨兵。
    这类"用合法取值当哨兵"的写法与缺陷 2（`start == 0`）是同一个错误模式，
    也与不变量"缺值不渲染 0%"同源。

40. **SPKI 指纹不支持无填充 base64，Agent 直接起不来**。
    运维常见的取值命令是 `openssl … | base64 | tr -d '='`（去掉填充），
    而 `parsePins` 只试 `base64.StdEncoding`，遇到无填充输入判为"格式非法"——
    明明一个字节都不差，节点却拒绝启动（`client.New` 直接返回错误）。
    另外从终端/文档/Markdown 表格复制时指纹里常夹空白，同样会失败。
    修复 = 先剥掉所有空白，`StdEncoding` 失败后回退 `RawStdEncoding`，
    再统一重编码成标准带填充形式参与比较。
    教训：**指纹是人工搬运的，解析器必须容忍人工搬运的常见产物**。

41. **`config.splitList("")` 返回空切片，让 Master 下发"不过滤任何网卡"**。
    `nic_exclude` 未配置时序列化出来是 `[]` 而不是 `null`，
    Agent 反序列化成**非 nil 空切片**，绕过 `ApplyServerConfig` 的 `!= nil` 守卫，
    于是内置的 `lo/docker*/veth*` 默认排除项被整体抹掉：
    流量统计把容器网卡与回环一起算进去，数字凭空虚高，
    而配置文件、日志、后台界面全都"看起来正常"。
    这是 `public.cards` 那条三态教训（不变量 6）在另一个字段上的重演。
    修复 = 未设置时返回 `nil`，并补生产端护栏（`TestBuildEffectiveEmitsNullForUnsetNICLists`
    直接断言报文里必须是 `"nic_exclude":null`；只断言 Go 侧的 `!= nil` 是不够的，
    真正决定 Agent 行为的是 JSON 里那个 null）。

42. **改了网卡过滤项永远不生效：`collector` 从不重建**。
    `collector.New(Options{...})` 在**构造时**就捕获了 `NICInclude/NICExclude/DiskPaths`，
    而 `syncConfig` / `Reload` 只替换了 prober、没有重建 collector。
    于是后台改完网卡过滤，Agent 一直按老规则统计，没有任何提示——
    与"改间隔要重启才生效"是同一类缺陷，只是藏得更深。
    修复 = 在两处同步路径里重建 collector（构造本身无 I/O，代价可忽略），
    并在测试里断言**两个实例都换了**（只断言"配置写进磁盘了"是不够的）。

43. **`splitList` 不认制表符与回车，会生成"幽灵网卡条目"**（本轮补生产端护栏时发现）。
    这些值是人从终端、表格、Windows 浏览器里剪贴进来的：`"lo,\t docker*"` 会被切出
    一个条目 `"\t"`，它匹配不到任何接口——既不生效也不报错，
    只在序列化后的 `config_version` 里留下噪声。函数注释写的是"逗号/空白分隔"，
    实现却只认空格与 `\n`。修复 = 把 `\t` 与 `\r` 也当分隔符。
    与缺陷 40 是同一个教训：**人工输入的分隔符种类必须按最宽的情况认**。

44. **PowerShell 脚本在中文 Windows 上"整份语法错误"：文件没有 UTF-8 BOM**（本轮写部署脚本时发现）。
    `scripts/*.ps1` 里有中文提示，而文件是 UTF-8 **无 BOM**。
    `powershell.exe`（5.1，不是 `pwsh`）读 `*.ps1` 时**只看 BOM** 判断编码，
    没有 BOM 就按当前 ANSI 代码页解码；中文 Windows 是 GBK，解码错位后某个汉字的
    尾字节会**吞掉紧跟其后的引号**，于是整份脚本报十来处「表达式或语句中包含意外的标记」，
    `powershell -File scripts\install.ps1` 完全跑不起来——**与脚本逻辑毫无关系**，
    而且在英文 locale 的机器上不会复现（cp1252 逐字节映射，不会吞后一个字符）。
    修复 = 5 个 `.ps1` 全部加 BOM。
    判定依据是把文件交给 PowerShell 自己的解析器（`Parser::ParseFile`）逐个数错误：
    加 BOM 前 `install.ps1` 3 处、`deploy-master.ps1` 11 处，加 BOM 后全部 0 处。
    **`scripts/build.ps1` 与 `scripts/setup-dev-env.ps1` 一直带着这个缺陷。**

45. **BOM 又不能出现在分发给节点的文本里**（缺陷 44 的修复引入的第二个面）。
    官方的一行安装命令是 `& ([scriptblock]::Create((irm .../install.ps1))) -Code '...'`，
    而脚本块构造 API 会把开头的 `U+FEFF` 当成第一个标识符的一部分，
    实测报「无法将“U+FEFF + Write-Output”项识别为 cmdlet」——**一行安装命令直接失败**。
    于是同一个文件对两个消费者的要求正好相反：**磁盘要 BOM（给 `-File` 用），
    线上不要 BOM（给脚本块用）**。修复 = 在 `serveInstallScript` 一处剥掉 BOM，
    并同时断言两侧（磁盘副本有 BOM + 响应体无 BOM），因为两个方向都是静默失效。
    教训：**当同一个产物有两个消费者时，差异要在一个地方抹平并有断言**，
    否则下次有人"顺手统一下编码"就会打断其中一条链路。

46. **本机与 CI 的构建路径没注入发布标签：32 位 ARM 节点永远升不了级**（本轮自查发现）。
    Makefile 的 `dist` 目标注入了 `PlatformTag`，但 `scripts/build.ps1 -Dist` 与
    `scripts/ci-cross.sh` 没有——而**这两条才是本机与 CI 实际用的构建路径**
    （这台机器没有 make）。后果是那些产物里的标签为空，退回运行时推断得到
    `linux_arm`，而发布矩阵里只有 `_armv7`/`_armv6`，于是树莓派一类的节点
    自升级永远报"该平台未发布此版本"。`-X` 指向不存在的符号时 `go build` **不报错**，
    什么也不注入——这是典型的"静默失效"，所以顺带让 `probe-agent version` 把标签打印出来，
    把不可观测变成可观测。

47. **`install.sh` 与发布布局对不上：一键安装会在"无法获取校验和"处中止**（本轮写部署文档时发现）。
    安装脚本取的是**扁平**路径（`$DIST_BASE/probe-agent_linux_amd64` 与
    `$MASTER_URL/dist/SHA256SUMS`，脚本并不知道版本号），而 `dist pull`、后台"发布文件"页、
    README 用的都是**带版本**的 `data/dist/<版本>/`。两者对不上时，
    按文档做完 `dist pull` 之后一键安装必然失败，而 Master 侧一切看起来都正常。
    修复 = 在 `handleDist` 里把扁平路径当作**最新版本的别名**（先按字面找，找不到再落到
    最新版本目录），只作用于单段路径。为什么不是"拉取时再拷一份到根目录"：
    那样会出现两份物理副本并必然漂移，表现为"新装节点拿到旧二进制、老节点却升级到新版本"
    的版本错位，且没有任何报错——别名只有一个来源，不可能错位；
    解析用的 `latestDistVersion` 与自升级是同一个函数，所以两条链路的"最新"永远一致。

48. **一键部署脚本把配置、主密钥与数据库都留给了 root，而服务以 `probe` 运行**（本轮自查发现，脚本还没上过真机）。
    systemd 单元是 `User=probe`，但脚本里建目录、写配置、`init-admin` 全部以 root 执行，
    而目录的 `chown` 发生在**文件被创建之前**——覆盖不到后来的新文件。于是
    `master.yaml`(0640 root)、`master.key`(0600 root)、`probe.db`(0644 root) 服务都读不了/写不了：
    表现是"部署完服务起不来、健康检查 20 秒探不到公开 API"，而脚本自己每一步都打印成功。
    修复 = `init-admin` **之后**再统一 `chown -R` 一次，并把最终权限 `ls -l` 打出来。
    顺带纠正一个假检查：以 root 跑 `test -r` 永远为真，那种"可读性检查"等于没检查。
    教训：这类脚本最容易错的地方是**顺序**与**看不见的状态**（谁属主、还能不能读）。

49. **一键部署脚本把 `install.master_url` 写成 `http://0.0.0.0:8080`**（本轮自查发现）。
    `install.master_url` 是**下发给 Agent** 的地址，而 `0.0.0.0` 是"监听所有网卡"的写法、
    不是可连接的目的地址：Agent 拿到它连不上自己那台机器，且这个错要到**装第一台 Agent**
    时才暴露。修复 = 没给 `--public-origin` 就**不写**该键（服务端本就有"按请求 Host 回填"的兜底），
    并在结尾明确提示"明文 HTTP 直连 IP 的部署必须手工补 `install.master_url`"。
    同一处还修了健康检查：拿 `0.0.0.0`/`[::]` 去探同样是错的
    （Linux 上连 `0.0.0.0` 被当成 localhost 只是实现细节，`::` 在多数系统上直接失败）。

50. **部署脚本往 `master.yaml` 里写了一个根本不存在的 `install:` 段——所有 `install.*` 配置静默失效**
    （本轮自查发现，脚本还没上过真机）。`install.mode` / `install.master_url` / `install.dist_base`
    全都是**数据库设置**（代码里用 `repo.GetSettingDefault("install.master_url", ...)` 读），
    `MasterConfig` 结构里**没有** `install` 这个键，而 `yaml.Unmarshal` 是**非严格**的：
    写了不报错、也**永远不生效**。更糟的是 `--dist-base` 还对外宣称"写进配置"——
    接受参数、生成一行 YAML、实际什么都没发生。
    这类"静默失效"最难发现：配置文件里白纸黑字，后台设置页却是空的，只能靠人比对。
    修了三处：① 两个部署脚本都**不再生成** `install:` 段，改为在结尾指向管理端
    「设置 → 安装与下载」（`--dist-base` 单独提示该填到哪里）；
    ② `LoadMaster` 改为**严格解析**（`yaml.NewDecoder` + `KnownFields(true)`），
    未知键变成**启动即报错**——把这一整类问题从"静默"改成"炸在启动"；
    ③ 新增 2 条变异（退回宽松模式、报错不点名键名）验证这道新护栏，
    并顺带让已有的"模板必须可加载"测试同时成为"模板不得含未知键"的守卫。

51. **一次被中断的变异运行留下了变异体，而我当时已经报出了"全库全绿"**（本轮自查发现）。
    残留点是 `internal/db/migrate.go` 的 `appliedVersions()`：
    `SELECT version FROM schema_migrations` 被改成了 `SELECT 0`，
    读回的"已应用集合"永远是 `{0:true}`，于是每次启动都重跑 `0001_init.sql`、
    报 `table settings already exists`（`TestMigrateIsIdempotent` 立刻变红）。
    同一轮里还有第二处被掩盖的真相：`internal/agent/updater/updater_test.go`
    有一处 `if _, err := Upgrade(...); err == nil { ... }` 之后又去断言 `err.Error()`——
    `err` 的作用域只在那个 `if` 里，**这个测试包当时根本编译不过**，
    所以它覆盖的那几条变异其实一条都没验到。
    三条教训：① **变异运行期间不能改文件、也不能强杀**——脚本每轮开始都先从快照整份回写，
      所以同时只会有一个文件带残留；强杀会让 `atexit` / 信号处理没跑完，残留就留在盘上；
    ② 判断有没有残留，`mutate.py` 的 `preflight()` 本身就是探针（所有锚点都命中才算干净），
      比 `go test` 更直接；
    ③ **报"全绿"必须以当次 `go test ./...` 的退出码为准**，不能沿用上一轮的结论——
      我这次就是把更早一轮的结果当成了当前状态。

52. **门控重写时丢掉了 ACME http-01 豁免：证书续期会在几周后必然失败**（本轮自查发现，端到端冒烟抓出）。
    重写 `siteGate` 时我把"该按哪份清单判"与"怎么比对"写在了一起，于是原本长在 `hostGate`
    里的 `/.well-known/acme-challenge/` 豁免，在新增的那条分支上就没有了。ACME 的 http-01
    校验是 CA **按 IP** 发起、Host 里写的也是 IP 字面量，所以只要配了域名白名单，
    续期请求一定被 421 挡下。这个缺陷的可怕之处在**时间尺度**上：部署当天一切正常，
    几周后证书到期、续期失败，而排查方向会先落到 DNS、反代、CA 限流上——
    与"域名白名单"看上去毫无关系。
    修复不是"在那条分支上再补一个豁免"，而是把比对整块交回 `hostGate`
    （一份实现、一处豁免、一处端口归一化），`siteGate` 只负责选出 `allowed`。
    **教训：同一件事有两处实现时，迟早有一处漏掉边界条件；正确做法是让第二处不存在。**

53. **"改完设置即时生效"是假的：门控在装配时把清单冻结成了闭包变量**（本轮自查发现，
    **只有端到端冒烟能抓到**）。单元测试里门控是就地构造的（构造完立刻发请求），
    所以 19 条用例全绿；而冒烟里门控是**进程启动时装配一次**、设置是**随后**改的。
    于是"切成分离"之后公开域名照样能打开后台——界面上显示已切换成功，日志里没有任何异常，
    没有任何一处会说"你看到的和生效的不是一回事"。
    修复 = 形态与清单在**每次请求**里现读，并用 `TestSiteGateReadsSettingsPerRequest`
    把这条钉死（该用例只构造一次门控，然后改设置、断言行为跟着变），另加一条
    "把清单冻结在构造时"的变异。**教训：测试的构造顺序与被测系统的真实生命周期不一致时，
    护栏验的是另一个系统；生命周期相关的不变量必须有一条按真实生命周期跑的用例（这里是冒烟）。**

54. **一条"变异未变红"的真相：锚点挂错了测试，而不是护栏不严**（本轮变异验证发现）。
    第 145 条变异把 `settingDefaults["site.layout"]` 从 `auto` 改成 `split`，测试依然全绿。
    查下去发现**默认值写了两份**：设置页那一份（`handleGetSettings` 会把 `settingDefaults`
    合并进响应，显示为"当前生效值"）与门控的回落值——后者是 `SiteLayoutMode` 里另写的字面量
    `siteLayoutAuto`。两者对不上的症状是"设置页显示已分离、实际仍在跟随配置文件"，
    与缺陷 53 同属"看到的和生效的不是一回事"。
    修复 = 新增 `siteLayoutDefault()` 统一从 `settingDefaults` 取回落值，门控用的就是
    管理员看到的那一份；改完复跑，第 145 条立刻变红。
    **教训：变异报"未变红"时，先问"它到底改到了谁"，再判护栏——把锚点挂到一个
    根本不经过该数据的用例上，是第三种假绿（前两种是"测试与实现走同一条捷径"
    和"替身比真身宽松"）。**

55. **一条"看天吃饭"的护栏：断言依赖了真实 DNS，而脚下这张网会把任何域名都解析成功**
    （本轮改完 `vendor` 提交策略后跑全库测试时暴露，`internal/agent/prober`）。
    `TestProbeResolveFailureIsNotReportedAsBlockedTarget` 用 `no-such-host.invalid`
    断言"解析不了的域名必须报错"。`.invalid` 是 RFC 2606 保留域名，正常网络下必然 NXDOMAIN，
    但这台机器上它被解析成了 `198.18.0.25`（沙箱流量拦截；Captive Portal 与运营商劫持页
    是同一个行为），而且**真的能连上 80 端口**——于是"探不通"变成了"探得通"，
    `s.Error == ""` 直接失败。判定它不是回归的依据：**未改动的 `server-probe` 上同样失败**，
    且 `internal/agent/prober` 这次一个字都没改。
    真正的问题是**护栏在测网络**：本包测试文件开头本来就写着"刻意不做依赖外网的断言"，
    这条恰好违背了它，于是"同一份代码在 A 机器红、在 B 机器绿"。
    修复 = `prober.go` 新增 `var lookupIP = net.LookupIP` 接缝（两处调用改走它），
    测试用 `stubLookupIP` 注入确定结果（`no-such-host.invalid` 刻意不在表里 → 返回 `IsNotFound`），
    并额外断言"替身必须已生效"——否则注入失效时这条用例会悄悄退回依赖真实 DNS。
    同时**补上了第一条针对该行为的确定性变异**：早先 148 条里没有一条覆盖
    "解析失败被报成 `blocked_target`"这个旧缺陷，这次借接缝补上，且它的判据不依赖本机 DNS：
    ```
    [OK] 86 解析失败又被报成 S4 拦截（域名拼错显示成「目标被拒绝」，且永不告警）
         → TestProbeResolveFailureIsNotReportedAsBlockedTarget 变红
    ```
    **教训：护栏的输入若来自外部世界（DNS、时钟、网络），它首先验证的是那个外部世界。
    这类断言要么注入替身，要么就只能承认它只在你自己的机器上成立。**
